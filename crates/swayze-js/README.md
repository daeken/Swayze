## Supported slice

`parse_script` parses a JavaScript Script with zero or more initialized `const` or `let` declarations, simple assignments, and braced `if` statements in source order, followed by one required expression. Call `Script::evaluate_value` for the final expression's `Value::Number(f64)` or `Value::Boolean(bool)`. For example, `let x = 0; if (true) { x = 42; } else { x = 2; } x` returns `Value::Number(42.0)`. The compatibility method `Script::evaluate` returns a Number as `f64` and reports `EvalError::NonNumericResult` for a Boolean without converting it. `prepare` is still an unsupported compatibility shim.

`Value`'s Rust `PartialEq` compares matching variants and their payloads; `f64` equality treats signed zeros as equal and NaN as unequal to itself. This is a host-side convenience, not a definition of guest JavaScript equality.

```text
Script   ::= (Decl | Assign | If)* Expr ';'? EOF
Decl     ::= ('const' | 'let') Name '=' Expr ';'
Assign   ::= Name '=' Expr ';'
If       ::= 'if' '(' Expr ')' Branch ('else' Branch)?
Branch   ::= '{' Assign* '}'
Expr     ::= Or ('?' Expr ':' Expr)?
Or       ::= And ('||' And)*
And      ::= Equality ('&&' Equality)*
Equality ::= Relation (('===' | '!==') Relation)*
Relation ::= Sum (('<' | '<=' | '>' | '>=') Sum)*
Sum      ::= Product (('+' | '-') Product)*
Product  ::= Unary (('*' | '/' | '%') Unary)*
Unary    ::= ('+' | '-' | '!') Unary | Primary
Primary  ::= Decimal | 'true' | 'false' | Name | '(' Expr ')'
Name     ::= [A-Za-z_$] [A-Za-z0-9_$]*  (subject to exclusions below)
Decimal  ::= (Integer ('.' [0-9]*)? | '.' [0-9]+) Exponent?
Integer  ::= '0' | [1-9] [0-9]*
Exponent ::= [eE] [+-]? [0-9]+
```

ECMAScript WhiteSpace, LineTerminator characters, `//` line comments, and `/* ... */` block comments are trivia: they are allowed between tokens and at source boundaries, but cannot join parts of a token. A line comment ends at LF, CR, U+2028 (line separator), U+2029 (paragraph separator), or EOF. A block comment is non-nesting and ends at the first `*/`; EOF before it is a malformed block comment. A line terminator inside a block comment counts as a line break between the surrounding tokens for diagnostics, but does not cause semicolon insertion.

Prefix `+`, `-`, and `!` associate to the right and bind tighter than `*`, `/`, and `%`, which share a precedence level above binary `+` and `-`. All binary operators associate to the left. Binary arithmetic binds tighter than the relational operators `<`, `<=`, `>`, and `>=`, which in turn bind tighter than the strict equality operators `===` and `!==`. For example, `3 < 2 < 1` compares the Boolean result of `3 < 2` with `1`; it does not test two relations between the original operands. The conditional operator `?:` binds less tightly than all of these operators and associates to the right: `a ? b : c ? d : e` means `a ? b : (c ? d : e)`. Both arms are parsed and checked against the same subset, but at evaluation time only the selected arm runs. `ToBoolean` leaves Booleans unchanged and maps Numbers `+0`, `-0`, and NaN to false, all other Numbers (including both infinities) to true. The result is the selected arm's value without coercion. A single `/` not starting a comment or longer punctuator is division only after an operand; regular expression literals are outside the slice. The lexer takes the longest match for these operator families: `===` and `!==` are single comparison tokens, separate from the simple assignment token `=`. Unsupported `==`, `!=`, `<<`, `>>`, `>>>`, `<<=`, `>>=`, and `>>>=` are rejected as whole punctuators, as are longer operators such as `++`, `--`, `/=`, `%=`, `**`, `??`, `??=`, and `?.`.

Names are case-sensitive ASCII tokens. `const`, `let`, `if`, `else`, `true`, and `false` are recognized only as whole tokens and cannot be used as names (`const0`, `let_`, `if0`, `else$`, `true$`, and `false0` are names). Other ECMAScript reserved words and literals, strict-mode reserved words, and Unicode and escaped names are outside this slice. We also exclude `await`, `as`, `async`, `from`, `get`, `of`, `set`, `using`, `eval`, `arguments`, `undefined`, `Infinity`, `NaN`, and `globalThis`. Each declaration has one name and an initializer. A statement starting with a name and a single `=` is a simple assignment, not an expression. Declarations and assignments require explicit semicolons; only the final expression's semicolon is optional. There is no automatic semicolon insertion (ASI).

A read must resolve to a `const` or `let` declared earlier in the same Script. An assignment target must resolve to an earlier `let`; its right-hand side can read the target's current value. Duplicate declarations, including mixed `let`/`const` pairs, are static errors (`Malformed` at the second name). Self, forward, and unbound reads and unavailable assignment targets are rejected as `Unsupported` at the name; writes to `const` are rejected as `Unsupported` at `=`. This subset does not model the temporal dead zone, runtime `ReferenceError` or `TypeError`, or global lookup. Evaluation initializes immutable `const` slots and mutable `let` slots and applies assignments in source order. Each slot holds a tagged Number or Boolean; assignment may change the type in a `let` slot. Slots are fresh for every evaluation, and neither scripts nor evaluations share binding state. No callbacks or objects are involved.

An `if` statement evaluates its parenthesized test using the same `ToBoolean` rules as `?:` and executes only the selected branch. A falsy test without `else`, or a selected empty branch, performs no writes. The parser checks both branches, even if one will not execute. Both branches require braces and can contain only zero or more simple assignments with explicit semicolons, targeting `let` bindings declared before the `if`. Nested `if` and `else if`, branch declarations, branch expression statements, and implicit completion values are not supported. An `if` statement has no trailing semicolon in this grammar and does not replace the final expression.

A decimal literal is one token, with no whitespace or comments inside it. It may include a decimal point (`.5`, `1.`, `1.25`), an exponent (`1e3`, `1E-3`), or both (`1.e3`). A sign before the mantissa is a unary operator; a sign after `e` or `E` is part of the exponent. Property access and spread, identifier suffixes, numeric separators, BigInt, nondecimal bases and legacy leading-zero integers are outside the slice.

Decimal literals are rounded directly to binary64 (nearest, ties to even), including positive infinity on overflow and subnormals or positive zero for sufficiently small magnitudes. There is no intermediate integer truncation or separate rounded scaling by the exponent. Unary `+` and `-` and binary `+`, `-`, `*`, `/`, and `%` use `ToNumber` on each operand: Numbers are unchanged, `true` becomes `1`, and `false` becomes `+0`. These operators return Numbers and work on binary64, including signed zeros, infinities, and NaN. Binary `+` has no string or BigInt cases in this subset. Remainder truncates the exact quotient toward zero without rounding it to binary64 first; a zero remainder has the sign of the dividend.

Logical `!` negates `ToBoolean` and returns a Boolean. `&&` preserves a falsy left operand and `||` preserves a truthy left operand; otherwise they evaluate and return the right operand, without coercing the result. Equality binds tighter than `&&`, then `||`, then `?:`. Bitwise `&` and `|` and logical assignment are unsupported. Skipped logical operands must still parse and count toward the instruction ceiling.

Comparisons always return a Boolean. Strict equality (`===`) does not coerce its operands: differing tags compare unequal, same-tag Booleans compare by value, and same-tag Numbers compare by binary64 equality (`+0` and `-0` are equal, NaN is unequal to every value including itself, and infinities compare equal only when their signs match). Strict inequality (`!==`) negates that result. The relational operators convert both operands with `ToNumber` and compare them numerically. Signed zeros compare as equal, `-Infinity` is below every finite Number and `+Infinity` is above every finite Number, and all four relational operators return false if either operand is NaN.

Diagnostics distinguish malformed syntax encountered in this grammar from unsupported input. `Unsupported` does **not** mean the input is valid JavaScript; rejecting an out-of-slice construct does not require validating the rest of it. For example, `1 +`, `(1 + 2`, `1e+`, and `1/*` are malformed, whereas `1..toString()`, `1e2_3`, `2**3`, an empty or trivia-only Script, and `1; 2` are unsupported. Both `1 2` and `1/**/2` are malformed; with a line break between the numbers (including inside a block comment), the input is unsupported rather than accepted by automatic semicolon insertion. A successful parse always accounts for the complete source, including anything after the optional semicolon. Spans are half-open UTF-8 byte ranges. An unterminated block comment spans from its opening delimiter to EOF; errors located at EOF itself use an empty range. Errors do not retain or print source text.

## Bounds and evidence

The default ceilings are 64 KiB of source, 4,096 tokens, a combined depth of 128 open parentheses (including the required parentheses of an `if` test) and pending conditional expressions, and 128 Ki work units. `parse_script_with_limits` takes explicit per-call limits. Tokens include names, declarations, literals, and punctuation but not trivia or EOF. A Boolean literal consumes one token and contributes its scanned bytes and one instruction emission to the work meter, with no decimal-conversion charge. The work meter charges consumed source bytes (including whitespace and comment delimiters and bodies), decimal-conversion input bytes, pushes of pending operators (including comparisons), opening-parenthesis markers and conditional arm markers, and emitted instructions (including jumps for `?:` and `if`); units are not cycle counts. Reads, assignment targets, and duplicate checks scan the previous declarations, charging one unit per candidate plus the name's byte length when the lengths match, before comparing the text. Many declarations can exhaust the work budget even when source and token limits are not reached. The one-token lookahead after a top-level name or the first branch of an `if` uses the same lexer and preserves the token's span and preceding line-break flag without rescanning or recharging it. Finite lookahead, amortized vector growth and bounded conversion keep the other work bounded. Literals with a decimal point or exponent have a fixed inclusive ceiling of 4,096 bytes per literal (`Limit::DecimalLiteralBytes`), independent of caller limits. Integer-only literals of 310 digits or more necessarily round to infinity and need no conversion after lexing; the same shortcut is not applied to fractions or exponents. All other decimal literals use Rust's `f64` parser within the conversion bound.

Parsing, evaluation and artifact destruction are iterative, not recursive. Scratch storage and output are proportional to the token count; vector growth is fallible. The private instruction sequence retains no source text or names: each read and assignment carries a numeric slot index, and each initialization consumes its expression's sole result and appends the next slot with the declaration's mutability. An assignment consumes its right-hand side's sole result and does not leave a value on the operand stack. The parser checks operands and expression stack balance. Tests for `?:` and `if` are popped by a conditional forward jump with an absolute instruction index (one-past-end denotes exit). The parser patches jumps to the current emission frontier. For `?:`, both arms start at the same post-test stack depth and each adds exactly one value at the join. For `if`, each branch starts and ends with an empty operand stack: the conditional jump skips to `else` if present or directly to the join otherwise. When `else` is present, a second forward jump skips it after the true branch. Peak operand depth accounts for both paths without adding their separate stack requirements together. Prefix chains use the token and work budgets, not the nesting budget. A successful parse does not execute initializers, assignments, or the final expression.

The separate evaluator accepts at most 4,096 total instructions, including both arms, their jumps, reads, initializations, and assignments, even when the parser is given higher limits. It checks forward jump indices, so each step advances the instruction pointer and no instruction can execute twice. The ceiling bounds temporary storage to at most 2,048 tagged operand slots and 2,047 tagged binding slots, each holding a Number or Boolean. The evaluator checks that reads target initialized slots, initializations fit the reserved storage, and assignments target initialized mutable slots.

The crate tests cover precedence/associativity, numeric rounding, lexical and keyword boundaries, complete-input rejection, UTF-8 spans, and parse and evaluation limits. Binding tests cover slot order and bounds, mixed declarations and assignments, rejected `const` writes and unavailable names, source retention, isolated repeat evaluation, and assignment counting at the evaluator cap. Lookahead tests cover exact token/work budgets, UTF-8 spans, comments, and rejection of assignment expressions or trailing statements. Comment tests cover all four line terminators and ASI-related diagnostics, EOF, non-nesting, operator and token boundaries, explicit semicolons, and exact UTF-8 work and source budgets. Conditional tests cover Number and Boolean truthiness, selected-type preservation, precedence and nested grouping, binding statements, malformed delimiters and longer punctuators, emitted targets and stack depth, and iterative nesting limits. Typed value tests cover Boolean literals versus keyword-like names, exact work and token budgets, type changes in lexical slots, arithmetic conversion including signed zero and NaN, and the typed and numeric result APIs. Comparison tests cover tagged results, strict equality without coercion, relational Boolean conversion, signed zeros, NaN and infinities, mixed-precedence chains, conditional integration, maximal-munch error spans and exact token/work and evaluator limits. Statement-level `if` tests cover selected writes (and unchanged skipped writes), empty branches and omitted `else`, fresh slots, expression precedence and truthiness, exact keyword boundaries, jump targets and stack balance, and rejection and resource accounting for both bodies even when skipped. Evaluator tests also show that only the selected arm executes, invalid reached jumps fail, and even skipped instructions count at the ceiling. Run `cargo test --frozen -p swayze-js` (also with `--release`) and `cargo clippy --frozen -p swayze-js --all-targets -- -D warnings` with the pinned toolchain. These are focused tests, not a formal proof, a full ECMAScript conformance run or browser deployment evidence.

## Gaps

This is a standalone prototype against ECMA-262, 16th edition (2025), especially its lexical grammar, decimal and Boolean literals, `ToBoolean` and `ToNumber` for these types, strict equality and relational comparison, and expression grammar. It does not implement general Script or Module syntax or their full early-error rules, ASI, value types other than Number and Boolean (including strings, BigInt, `null`, and objects), other coercions, loose equality (`==`, `!=`), shift operators and other unary or binary operators, calls, host hooks, general blocks or block scope, nested `if` statements, globals, other declaration forms (including uninitialized `let`), loops, assignment expressions, chained or compound assignments, regular expression literals, hashbang comments or Annex B behavior (including HTML-like comments), alternate numeric literal syntax or JavaScript source represented as arbitrary UTF-16 code units. It does not implement host cancellation, general JavaScript execution, or renderer integration. Allocator, toolchain and platform behavior are outside the parser's guarantees.
