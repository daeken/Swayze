## Supported slice

`parse_script` parses a JavaScript Script with zero or more numeric `const` declarations followed by one arithmetic expression. Call `Script::evaluate` on that artifact to get the final expression's `f64` result. For example, `const x = 2; const y = x * 5; y + 1;` evaluates to `11`. `prepare` is still an unsupported compatibility shim.

```text
Script   ::= Const* Sum ';'? EOF
Const    ::= 'const' Name '=' Sum ';'
Sum      ::= Product (('+' | '-') Product)*
Product  ::= Unary (('*' | '/' | '%') Unary)*
Unary    ::= ('+' | '-') Unary | Primary
Primary  ::= Decimal | Name | '(' Sum ')'
Name     ::= [A-Za-z_$] [A-Za-z0-9_$]*  (subject to exclusions below)
Decimal  ::= (Integer ('.' [0-9]*)? | '.' [0-9]+) Exponent?
Integer  ::= '0' | [1-9] [0-9]*
Exponent ::= [eE] [+-]? [0-9]+
```

ECMAScript WhiteSpace, LineTerminator characters, `//` line comments, and `/* ... */` block comments are trivia: they are allowed between tokens and at source boundaries, but cannot join parts of a token. A line comment ends at LF, CR, U+2028 (line separator), U+2029 (paragraph separator), or EOF. A block comment is non-nesting and ends at the first `*/`; EOF before it is a malformed block comment. A line terminator inside a block comment counts as a line break between the surrounding tokens for diagnostics, but does not cause semicolon insertion.

Prefix `+` and `-` associate to the right and bind tighter than `*`, `/`, and `%`, which share a precedence level above binary `+` and `-`. Binary operators associate to the left. A single `/` not starting a comment or longer punctuator is division only after an operand; regular expression literals are outside the slice. Longer JavaScript punctuators such as `++`, `--`, `/=`, `%=`, and `**` are not split into shorter supported operators.

Names are case-sensitive ASCII tokens; `const` is a keyword only at a whole-token boundary (`const0`, `const_`, and `const$` are names). Unicode and escaped names, ECMAScript reserved words and literals, and the strict-mode reserved words are outside this slice. We also exclude `await`, `as`, `async`, `from`, `get`, `of`, `set`, `using`, `eval`, `arguments`, `undefined`, `Infinity`, `NaN`, and `globalThis`. Each declaration has one name, an initializer, and an explicit semicolon; only the final expression's semicolon is optional. There is no automatic semicolon insertion (ASI).

A read must resolve to a `const` declared earlier in the same Script. Duplicate declarations are static errors (`Malformed` at the second name). Reads of self, forward, or unbound names are rejected as `Unsupported` at the read: this subset does not model JavaScript's temporal dead zone, runtime `ReferenceError`, or lookup in a global environment. Evaluation initializes the slots in source order; each slot is assigned once and holds a Number, including signed zero, infinity, or NaN. Slots are fresh for every evaluation, and neither scripts nor evaluations share binding state. No callbacks or objects are involved.

A decimal literal is one token, with no whitespace or comments inside it. It may include a decimal point (`.5`, `1.`, `1.25`), an exponent (`1e3`, `1E-3`), or both (`1.e3`). A sign before the mantissa is a unary operator; a sign after `e` or `E` is part of the exponent. Property access and spread, identifier suffixes, numeric separators, BigInt, nondecimal bases and legacy leading-zero integers are outside the slice.

Decimal literals are rounded directly to binary64 (nearest, ties to even), including positive infinity on overflow and subnormals or positive zero for sufficiently small magnitudes. There is no intermediate integer truncation or separate rounded scaling by the exponent. Each operation works on binary64 Numbers, including signed zeros, infinities, and NaN. Remainder truncates the exact quotient toward zero without rounding it to binary64 first; a zero remainder has the sign of the dividend.

Diagnostics distinguish malformed syntax encountered in this grammar from unsupported input. `Unsupported` does **not** mean the input is valid JavaScript; rejecting an out-of-slice construct does not require validating the rest of it. For example, `1 +`, `(1 + 2`, `1e+`, and `1/*` are malformed, whereas `1..toString()`, `1e2_3`, `2**3`, an empty or trivia-only Script, and `1; 2` are unsupported. Both `1 2` and `1/**/2` are malformed; with a line break between the numbers (including inside a block comment), the input is unsupported rather than accepted by automatic semicolon insertion. A successful parse always accounts for the complete source, including anything after the optional semicolon. Spans are half-open UTF-8 byte ranges. An unterminated block comment spans from its opening delimiter to EOF; errors located at EOF itself use an empty range. Errors do not retain or print source text.

## Bounds and evidence

The default ceilings are 64 KiB of source, 4,096 tokens, 128 nested parentheses and 128 Ki work units. `parse_script_with_limits` takes explicit per-call limits. Tokens include names, `const`, and punctuation but not trivia or EOF. The work meter charges consumed source bytes (including whitespace and comment delimiters and bodies), decimal-conversion input bytes, pushes of pending operators and opening-parenthesis markers, and emitted instructions; units are not cycle counts. Name resolution and duplicate checks scan the previous declarations, charging one unit per candidate plus the name's byte length when the lengths match, before comparing the text. Many declarations can exhaust the work budget even when source and token limits are not reached. Finite lookahead, amortized vector growth and bounded conversion keep the other work bounded. Literals with a decimal point or exponent have a fixed inclusive ceiling of 4,096 bytes per literal (`Limit::DecimalLiteralBytes`), independent of caller limits. Integer-only literals of 310 digits or more necessarily round to infinity and need no conversion after lexing; the same shortcut is not applied to fractions or exponents. All other literals use Rust's `f64` parser within the conversion bound.

Parsing, evaluation and artifact destruction are iterative, not recursive. Scratch storage and output are proportional to the token count; vector growth is fallible. The private postfix retains no source text or names: each read carries a numeric slot index, and each initialization consumes its expression's sole result and appends the next slot. The parser checks operands and expression stack balance. Prefix chains use the token and work budgets, not the parenthesis nesting budget. A successful parse does not execute initializers or the final expression. The separate evaluator accepts at most 4,096 instructions (including reads and initializations) even when the parser is given higher limits. That bounds temporary storage to at most 2,048 `f64` operand slots and 2,047 `f64` binding slots. The evaluator checks that each read addresses an initialized slot and each initialization fits the reserved storage.

The crate tests cover precedence/associativity, numeric rounding, lexical and keyword boundaries, complete-input rejection, UTF-8 spans, and parse and evaluation limits. Binding tests cover slot order and bounds, duplicate and unavailable names, source retention, and isolated repeat evaluation. Comment tests cover all four line terminators and ASI-related diagnostics, EOF, non-nesting, operator and token boundaries, explicit semicolons, and exact UTF-8 work and source budgets. Run `cargo test --locked -p swayze-js` (also with `--release`). These are focused tests, not a formal proof, a full ECMAScript conformance run or browser deployment evidence.

## Gaps

This is a standalone prototype against ECMA-262, 16th edition (2025), especially its lexical grammar, numeric literals and arithmetic expression grammar. It does not implement general Script or Module syntax or their full early-error rules, ASI, other unary or binary operators, calls, other declaration forms, loops, assignment expressions, regular expression literals, hashbang comments or Annex B behavior (including HTML-like comments), alternate numeric literal syntax or JavaScript source represented as arbitrary UTF-16 code units. It does not implement host cancellation, general JavaScript execution, or renderer integration. Allocator, toolchain and platform behavior are outside the parser's guarantees.
