## Supported slice

`parse_script` parses a JavaScript Script with zero or more initialized `const` or `let` declarations, simple assignments, and braced `if` and `while` statements in source order, followed by one required expression. Call `Script::evaluate_value` for the final expression's `Value::Number(f64)`, `Value::Boolean(bool)`, `Value::Null`, or `Value::Undefined`. For example, `let x = 0; if (true) { const answer = 42; x = answer; } else { x = 2; } x` returns `Value::Number(42.0)`. The compatibility method `Script::evaluate` returns a Number as `f64` and reports `EvalError::NonNumericResult` for any other result without converting it. The error variant is unchanged; its message is now `script result is not a Number`. `prepare` is still an unsupported compatibility shim.

`Value`'s Rust `PartialEq` compares matching variants and their payloads; `f64` equality treats signed zeros as equal and NaN as unequal to itself. This is a host-side convenience, not a definition of guest JavaScript equality.

```text
Script   ::= (Decl | Assign | If | While)* Expr ';'? EOF
Decl     ::= ('const' | 'let') Name '=' Expr ';'
Assign   ::= Name '=' Expr ';'
If       ::= 'if' '(' Expr ')' Block ('else' Block)?
While    ::= 'while' '(' Expr ')' Block
Block    ::= '{' (Decl | Assign | If | While | LoopJump)* '}'
LoopJump ::= ('break' | 'continue') ';'  (requires an enclosing While)
Expr     ::= (Or | Coalesce) ('?' Expr ':' Expr)?
Or       ::= And ('||' And)*
Coalesce ::= BitOr ('??' BitOr)+
And      ::= BitOr ('&&' BitOr)*
BitOr    ::= BitXor ('|' BitXor)*
BitXor   ::= BitAnd ('^' BitAnd)*
BitAnd   ::= Equality ('&' Equality)*
Equality ::= Relation (('===' | '!==') Relation)*
Relation ::= Shift (('<' | '<=' | '>' | '>=') Shift)*
Shift    ::= Sum (('<<' | '>>' | '>>>') Sum)*
Sum      ::= Product (('+' | '-') Product)*
Product  ::= Unary (('*' | '/' | '%') Unary)*
Unary    ::= ('+' | '-' | '!' | '~') Unary | Primary
Primary  ::= Decimal | 'true' | 'false' | 'null' | Name | '(' Expr ')'
Name     ::= [A-Za-z_$] [A-Za-z0-9_$]*  (subject to exclusions below)
Decimal  ::= (Integer ('.' [0-9]*)? | '.' [0-9]+) Exponent?
Integer  ::= '0' | [1-9] [0-9]*
Exponent ::= [eE] [+-]? [0-9]+
```

ECMAScript WhiteSpace, LineTerminator characters, `//` line comments, and `/* ... */` block comments are trivia: they are allowed between tokens and at source boundaries, but cannot join parts of a token. A line comment ends at LF, CR, U+2028 (line separator), U+2029 (paragraph separator), or EOF. A block comment is non-nesting and ends at the first `*/`; EOF before it is a malformed block comment. A line terminator inside a block comment counts as a line break between the surrounding tokens for diagnostics, but does not cause semicolon insertion.

From tightest to loosest, precedence is prefix `+ - ! ~`, multiplicative `* / %`, additive `+ -`, shifts `<< >> >>>`, relational `< <= > >=`, strict equality `=== !==`, bitwise `&`, bitwise `^`, bitwise `|`, logical `&&`, logical `||`, then conditional `?:` (see below for `??`). Prefix operators associate to the right and binary operators associate to the left. For example, `1 + 1 << 3` means `(1 + 1) << 3`, `2 & 1 === 0` means `2 & (1 === 0)`, and `3 < 2 < 1` compares the Boolean result of `3 < 2` with `1`, not two relations between the original operands. The conditional operator `?:` binds less tightly than all of these operators and associates to the right: `a ? b : c ? d : e` means `a ? b : (c ? d : e)`. Both arms are parsed and checked against the same subset, but at evaluation time only the selected arm runs. `ToBoolean` leaves Booleans unchanged and maps `null`, `undefined`, and Numbers `+0`, `-0`, and NaN to false, all other Numbers (including both infinities) to true. The result is the selected arm's value without coercion. A single `/` not starting a comment or longer punctuator is division only after an operand; regular expression literals are outside the slice. The lexer takes the longest match for these operator families: `===` and `!==` are single comparison tokens, separate from simple assignment `=`; `&&` and `||` are distinct from `&` and `|`; and `<<`, `>>`, and `>>>` are distinct from relational tokens. Unsupported punctuators such as `==`, `!=`, `++`, `--`, `**`, and `?.`, and compound assignments such as `&=`, `^=`, `|=`, `<<=`, `>>=`, `>>>=`, `&&=`, `||=`, and `??=` are rejected as whole punctuators.

Names are case-sensitive ASCII tokens. `const`, `let`, `if`, `else`, `while`, `break`, `continue`, `true`, `false`, and `null` are recognized only as whole tokens and cannot be used as names (`const0`, `let_`, `if0`, `else$`, `while0`, `break0`, `continue_`, `true$`, `false0`, and `null$` are names). Other ECMAScript reserved words and literals, strict-mode reserved words, and Unicode and escaped names are outside this slice. We also exclude `await`, `as`, `async`, `from`, `get`, `of`, `set`, `using`, `eval`, `arguments`, `Infinity`, `NaN`, and `globalThis`. Each declaration has one name and an initializer. A statement starting with a name and a single `=` is a simple assignment, not an expression. Declarations, assignments, `break`, and `continue` require explicit semicolons; only the final expression's semicolon is optional. There is no automatic semicolon insertion (ASI).

Each braced branch and loop body has its own lexical scope. Its test is in the enclosing scope, not in the new block. Reads and assignment targets resolve to the nearest declaration of that name in their own or an enclosing scope. A declaration shadows an enclosing name throughout its block, including before the initializer runs. The parser rejects reads and writes before that binding's initialization as `Unsupported` at the accessed name, including self-reads in the initializer and accesses in skipped branches or unreachable code. It does not fall back to an outer binding. An initialized `let` may be assigned; writes to an initialized `const` are `Unsupported` at `=`. Block names are not visible from sibling blocks or after scope exit. `undefined` is an identifier that block declarations can shadow, not a reserved word. A `let` or `const` declaration named exactly `undefined` at the Script root is `Malformed` at the name: a classic Script cannot lexically redeclare the non-configurable global property. Only if no declaration resolves does a read of `undefined` produce `Value::Undefined`; this immutable default is not stored in a binding slot. An unbound write to `undefined` or any other unbound access is `Unsupported` at the name. Duplicate declarations in one scope, including mixed `let`/`const` pairs, are `Malformed` at the second name. Disjoint blocks, including then/else arms, may reuse names. The subset does not implement a runtime temporal dead zone, `ReferenceError` or `TypeError`, or global lookup.

Evaluation runs initializers and assignments in source order along the paths taken. Each initializer that is reached on a block entry, including on repeated iterations, supplies a fresh value rather than retaining the prior entry's value. Each slot holds a tagged primitive value; assignment may change the type in a `let` slot. Slots are fresh for every evaluation, and neither scripts nor evaluations share binding state. No callbacks, closures, or objects are involved.

An `if` statement evaluates its parenthesized test using the same `ToBoolean` rules as `?:` and executes only the selected branch. A falsy test without `else`, or a selected empty branch, performs no writes. A `while` statement uses the same truthiness and evaluates its parenthesized test before every iteration, including the first. It executes the body in source order after a truthy result and exits after a falsy result. For example, `let n = 3; let sum = 0; while (n) { sum = sum + n; n = n - 1; } sum` returns `Value::Number(6.0)`.

Every branch and loop body requires braces and may contain initialized lexical declarations, simple assignments, and nested `if` and `while` statements. An `else` belongs to the `if` whose then-arm the preceding `}` closed; an `else` may contain a nested `if` only inside its own braces. Expression statements in blocks are outside the slice. Neither `if` nor `while` takes a trailing semicolon or replaces the required final expression.

`break;` exits the innermost enclosing `while` and resumes after its body. `continue;` skips the rest of that loop body and reevaluates its test using the current bindings. Intervening `if` blocks are not jump targets. Prior assignments to still-visible bindings are preserved, but bindings in exited scopes cannot be accessed. Neither jump produces a result. An unlabeled jump without an enclosing `while` is `Malformed` at the keyword, even in an inactive branch. Labels and labeled jumps are unsupported. The parser still checks every block and nested test, including code after a jump and branches or loops that will not execute.

A decimal literal is one token, with no whitespace or comments inside it. It may include a decimal point (`.5`, `1.`, `1.25`), an exponent (`1e3`, `1E-3`), or both (`1.e3`). A sign before the mantissa is a unary operator; a sign after `e` or `E` is part of the exponent. Property access and spread, identifier suffixes, numeric separators, BigInt, nondecimal bases and legacy leading-zero integers are outside the slice.

Decimal literals are rounded directly to binary64 (nearest, ties to even), including positive infinity on overflow and subnormals or positive zero for sufficiently small magnitudes. There is no intermediate integer truncation or separate rounded scaling by the exponent. Unary `+` and `-` and binary `+`, `-`, `*`, `/`, and `%` use `ToNumber` on each operand: Numbers are unchanged, `true` becomes `1`, `false` and `null` become `+0`, and `undefined` becomes NaN. These operators return Numbers and work on binary64, including signed zeros, infinities, and NaN. Binary `+` has no string or BigInt cases in this subset. Remainder truncates the exact quotient toward zero without rounding it to binary64 first; a zero remainder has the sign of the dividend.

Number bitwise operators first apply the same `ToNumber` coercion. `ToUint32` maps NaN, both infinities, and either signed zero to zero; otherwise it truncates the binary64 value toward zero and takes its nonnegative residue modulo 2^32. `ToInt32` interprets those same bits as a signed two's-complement integer. `~`, `&`, `^`, and `|` operate on `ToInt32` operands and return signed 32-bit results as Numbers. `<<` and `>>` use `ToInt32` on the left operand and return signed results (`>>` extends the sign bit); `>>>` uses `ToUint32` on the left and returns an unsigned result, filling with zeros. All three shifts use only the low five bits of `ToUint32` of the right operand. Integer zero results are always Number `+0`. For example, `-1 >> 1` returns `-1`, `-1 >>> 1` returns `2147483647`, and `1 << 33` returns `2`.

Logical `!` negates `ToBoolean` and returns a Boolean. `&&` preserves a falsy left operand and `||` preserves a truthy left operand; otherwise they evaluate and return the right operand, without coercing the result. `??` preserves a left operand that is neither `null` nor `undefined`; otherwise it evaluates and returns the right operand. Unlike `||`, it preserves `false`, signed zeros, and NaN. The result keeps the selected operand's original tag. `??` binds below all bitwise operators and above `?:`. Mixing `??` with `&&` or `||` in the same test or arm without parentheses is malformed at the second kind of operator. For example, `null ?? false || 7` is malformed, but `(null ?? false) || 7`, `null ?? (false || 7)`, and `true || false ? null ?? 7 : 8` are supported. Optional chaining and compound assignments (including `??=`) are unsupported. Skipped operands must still parse and count toward the instruction ceiling.

Comparisons always return a Boolean. Strict equality (`===`) does not coerce its operands: differing tags compare unequal, `null` equals only `null`, `undefined` equals only `undefined`, same-tag Booleans compare by value, and same-tag Numbers compare by binary64 equality (`+0` and `-0` are equal, NaN is unequal to every value including itself, and infinities compare equal only when their signs match). Strict inequality (`!==`) negates that result. The relational operators convert both operands with `ToNumber` and compare them numerically. Signed zeros compare as equal, `-Infinity` is below every finite Number and `+Infinity` is above every finite Number, and all four relational operators return false if either operand is NaN.

Diagnostics distinguish malformed syntax encountered in this grammar from unsupported input. `Unsupported` does **not** mean the input is valid JavaScript; rejecting an out-of-slice construct does not require validating the rest of it. For example, `1 +`, `(1 + 2`, `1e+`, and `1/*` are malformed, whereas `1..toString()`, `1e2_3`, `2**3`, an empty or trivia-only Script, and `1; 2` are unsupported. Both `1 2` and `1/**/2` are malformed; with a line break between the numbers (including inside a block comment), the input is unsupported rather than accepted by automatic semicolon insertion. A successful parse always accounts for the complete source, including anything after the optional semicolon. Reads and assignment targets are resolved after syntactic parsing, so a syntax or resource diagnostic during parsing can precede a binding access diagnostic. Spans are half-open UTF-8 byte ranges. An unterminated block comment spans from its opening delimiter to EOF; errors located at EOF itself use an empty range. Errors do not retain or print source text.

## Bounds and evidence

The default ceilings are 64 KiB of source, 4,096 tokens, a combined expression depth of 128 open parentheses (including the required parentheses of an `if` or `while` test) and pending conditional expressions, and 128 Ki work units. `parse_script_with_limits` takes explicit per-call limits. An additional fixed ceiling allows up to 128 simultaneously active `if` and `while` statements, counting a top-level control statement as one and keeping the same frame across both arms of an `if`. This is independent of the expression limit; exceeding it reports `Limit::NestingDepth` at the next control keyword.

Tokens include names, declarations, literals, and punctuation but not trivia or EOF. A Boolean or `null` literal consumes one token and contributes its scanned bytes and one instruction emission to the work meter, with no decimal-conversion charge. `undefined` is metered as an ordinary name, including the lexical search before fallback. The work meter charges consumed source bytes (including whitespace and comment delimiters and bodies), decimal-conversion input bytes, pushes of pending operators (including comparisons), opening-parenthesis markers, conditional arm markers and statement frames, and emitted instructions (including jumps for `?:`, short-circuit operators, `if`, and `while`); units are not cycle counts. A statement frame costs one unit at the opening `{` of a then-arm or loop body; an `else` reuses that frame. `break;` and `continue;` each emit one instruction, and patching a `break` costs one additional unit at its loop's closing `}`. A duplicate check scans earlier declarations in the same scope. After syntactic parsing, the resolver visits recorded accesses in source order. It searches the access's own scope and follows parent links outward until it finds a match or runs out of scopes. Within each scope the search visits declarations in reverse declaration order. The work meter charges one unit per candidate visited and one per hop to a parent scope; a same-length name comparison first charges the name's byte length. Sibling scopes are never searched. Many declarations or nested accesses can exhaust the work budget even when source and token limits are not reached. The one-token lookahead after a top-level name or the first branch of an `if` uses the same lexer and preserves the token's span and preceding line-break flag without rescanning or recharging it. Finite lookahead, amortized vector growth and bounded conversion keep the other work bounded. Literals with a decimal point or exponent have a fixed inclusive ceiling of 4,096 bytes per literal (`Limit::DecimalLiteralBytes`), independent of caller limits. Integer-only literals of 310 digits or more necessarily round to infinity and need no conversion after lexing; the same shortcut is not applied to fractions or exponents. All other decimal literals use Rust's `f64` parser within the conversion bound.

Parsing, evaluation and artifact destruction are iterative, not recursive. Scratch storage and output are proportional to the token count; vector growth is fallible. The parser records one scope per block plus the Script root, one entry per declaration (at least five tokens and two emitted instructions each), and one site per name read or write. An `else` reuses its control frame but has a distinct scope with the same parent as the then-arm. Tests record their access sites before their body scope opens. The resolver chooses the lexical binding before checking source order: the access must follow the declaration's terminating semicolon. Only then does it check mutability for writes and patch the instruction's operand. Each declaration has a distinct numeric slot assigned in source order. Each resolved lexical read, assignment, and initializer carries that slot index; an unbound read of `undefined` is patched to a primitive push instead. The private instruction sequence retains no source text, names, or scope metadata. Initializers consume the sole expression result and set or replace the designated slot with the declaration's mutability. An assignment consumes its right-hand side's sole result and does not leave a value on the operand stack. The parser checks operands and expression stack balance. Tests for `?:`, `if`, and `while` are popped by a conditional forward jump with an absolute instruction index (one-past-end denotes exit). The parser patches each forward jump once, through a checked instruction index, to the current emission frontier. Closing a statement arm or body performs at most one such patch plus one patch per `break` targeting that loop. A stored frame index finds the innermost loop in constant time; closing a loop restores the index of its enclosing loop. Each loop keeps its pending breaks linked through the jump operands, so patching visits each break once with no target searches or extra per-break allocation. For `&&`, `||`, and `??`, a taken forward edge keeps the left value and skips the right operand. The fallthrough path instead drops the left value; the right operand restores the same depth at the join. For `?:`, both arms start at the same post-test stack depth and each adds exactly one value at the join. The statement form consumes the sole operand, leaving an empty stack on either path. The parser checks for an empty operand stack and no pending expression at statement entry and at block close, including in nested blocks. For `if`, the conditional jump skips to `else` if present or directly to the join otherwise. When `else` is present, a second forward jump skips it after the true branch. For `while`, both the conditional exit and every `break` go just past the loop's back edge. A dedicated backward instruction at `continue` or at the end of the body returns to the first instruction of that frame's test. Emission requires an empty operand stack at unconditional statement jumps and a strictly backward target for each back edge. Peak operand depth accounts for all paths without accumulating across iterations. Prefix chains use the token and work budgets, not the nesting budget. A successful parse does not execute initializers, assignments, or the final expression.

No slot is cleared when control leaves a block. In a prepared Script, every reference points to the nearest declaration, and that declaration's initializer precedes the reference. Statement branches either enter a block at its start or skip it; jumps may leave scopes but cannot enter a suffix of a block from outside it. Back edges, including `continue`, retest the target loop before its body can run again. Thus a reference to a block binding can be reached only after that binding's initializer executed in the current entry of its declaring block; a jump skipping initialization also skips all uses for that entry. Exited slots are inaccessible until initialization on a subsequent entry, so unused or stale slots have no effect.

The evaluator first checks an inclusive ceiling of 4,096 prepared instructions (`EvalError::LimitExceeded`), including skipped paths and their jumps, even when the parser is given higher limits. This bounds temporary storage to at most 2,048 tagged operand slots and 2,047 optional binding slots (each declaration needs at least two instructions and the final expression at least one). Both vectors reserve storage fallibly; bindings start empty and untaken paths can leave them empty. The evaluator checks jump targets, requiring all edges except `LoopBack` to go strictly forward. `LoopBack` must go strictly backward. Both backward and forward unconditional statement jumps require an empty operand stack. Reads and writes must target initialized slots, initializers must target in-range slots and can replace only a value from the same initializer instruction, and assignments must target mutable slots. Malformed reached instructions are distinct from resource exhaustion (`EvalError::InvalidScript`).

Each evaluation gets a separate fixed budget of 16,384 dispatches. Every dispatched instruction costs one unit, including short-circuit branches, loop tests, `break`, `continue`, and regular loop back edges. Skipped instructions cost no dispatches, and reaching the end costs none. A script that finishes on dispatch 16,384 succeeds; if it needs another dispatch, evaluation stops before running that instruction and returns `EvalError::DispatchLimitExceeded`. Even `while (true) {}` costs three dispatches per complete iteration (literal, conditional jump, backward jump). The budget and all binding state reset on the next evaluation.

## Gaps

This is a standalone prototype against ECMA-262, 16th edition (2025), especially its lexical grammar, decimal, Boolean and `null` literals, `ToBoolean` and `ToNumber` for supported primitive values, `ToInt32` and `ToUint32`, Number bitwise operations, strict equality and relational comparison, and expression grammar. It does not implement general Script or Module syntax or their full early-error rules, ASI, value types other than Number, Boolean, Null, and Undefined (including strings, BigInt, and objects), other coercions, loose equality (`==`, `!=`), other unary or binary operators, calls, host hooks, standalone blocks or a runtime temporal dead zone, unbraced control bodies and `else if`, labels and labeled jumps, `switch`, general global lookup or writes, optional chaining, other declaration forms (including uninitialized `let`), other loop forms, assignment expressions, chained or compound assignments, regular expression literals, hashbang comments or Annex B behavior (including HTML-like comments), alternate numeric literal syntax or JavaScript source represented as arbitrary UTF-16 code units. It does not implement host cancellation, general JavaScript execution, or renderer integration. Allocator, toolchain and platform behavior are outside the parser's guarantees.
