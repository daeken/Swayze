## Supported slice

`parse_script` parses a JavaScript Script with zero or more `const` or `let` declaration statements (with one or more single-name declarators), assignments, increments and decrements (including comma suffixes), expression statements, standalone blocks, empty statements, and braced `if` and loop statements (`while`, classic `for`, and `do`–`while`) in source order, followed by one required expression. Standalone blocks, braced `if` chains, and loops may carry one or more consecutive label prefixes. Call `Script::evaluate_primitive` for the final expression's `PrimitiveValue::Scalar(Value)` or `PrimitiveValue::String(&[u16])`. A String result borrows immutable UTF-16 code units from the Script, including any unpaired surrogates. `Script::evaluate_value` still returns `Value::Number(f64)`, `Value::Boolean(bool)`, `Value::Null`, or `Value::Undefined`, and reports `EvalError::NonScalarResult` on a String result. For example, `let x = 0; if (false) { x = 1; } else if (true) { x = 42; } else { x = 2; } x` returns `Value::Number(42.0)` through `evaluate_value`. `Script::evaluate` still returns a Number as `f64` and reports `EvalError::NonNumericResult` for any other result, including String. Neither method coerces the result. `prepare` is still an unsupported compatibility shim.

`Value`'s Rust `PartialEq` compares matching variants and their payloads; `f64` equality treats signed zeros as equal and NaN as unequal to itself. This is a host-side convenience, not a definition of guest JavaScript equality.

```text
Script   ::= Stmt* Expr ';'? EOF
Stmt     ::= Decl | Write | ExprStmt | Block | Empty | If | Loop | Labelled | Jump
ExprStmt ::= Expr ';'
Empty    ::= ';'
Decl     ::= (ConstList | LetList) ';'
ConstList ::= 'const' ConstItem (',' ConstItem)*
LetList  ::= 'let' LetItem (',' LetItem)*
ConstItem ::= Name '=' Rhs
LetItem   ::= Name ('=' Rhs)?
Write    ::= Store (',' Rhs)* ';'
             (a leading assignment selects Write; a leading name update
              selects Write before ';' or ',' and Expr before a binary operator or '?')
Store    ::= Assignment | NameUpdate
Assignment ::= Name AssignOp Rhs
NameUpdate ::= UpdateOp Name | Name [no LineTerminator here] UpdateOp
UpdateOp ::= '++' | '--'
AssignOp ::= '=' | '+=' | '-=' | '*=' | '/=' | '%=' | '**=' | '&=' | '^=' | '|=' | '<<=' | '>>=' | '>>>=' | '&&=' | '||=' | '??='
If       ::= 'if' '(' Test ')' Block ('else' (If | Block))?
Labelled ::= (Name ':')+ (Block | If | Loop)
Loop     ::= While | For | DoWhile
While    ::= 'while' '(' Test ')' Block
For      ::= 'for' '(' (ConstList | LetList | ForExpr)? ';' Test? ';' ForExpr? ')' Block
ForExpr  ::= Store (',' Rhs)* | Expr
             (a leading assignment selects Store; a leading name update
              selects Store before ',' or the clause delimiter, and Expr
              before a binary operator or '?')
DoWhile  ::= 'do' Block 'while' '(' Test ')' ';'
Block    ::= '{' Stmt* '}'
Jump     ::= ('break' | 'continue') ([no LineTerminator here] Name)? ';'
Expr     ::= Conditional (',' Rhs)*
Test     ::= Rhs (',' Rhs)*
Rhs      ::= (Name AssignOp)* Conditional
Conditional ::= (Or | Coalesce) ('?' Rhs ':' Rhs)?
Or       ::= And ('||' And)*
Coalesce ::= BitOr ('??' BitOr)+
And      ::= BitOr ('&&' BitOr)*
BitOr    ::= BitXor ('|' BitXor)*
BitXor   ::= BitAnd ('^' BitAnd)*
BitAnd   ::= Equality ('&' Equality)*
Equality ::= Relation (('==' | '!=' | '===' | '!==') Relation)*
Relation ::= Shift (('<' | '<=' | '>' | '>=') Shift)*
Shift    ::= Sum (('<<' | '>>' | '>>>') Sum)*
Sum      ::= Product (('+' | '-') Product)*
Product  ::= Power (('*' | '/' | '%') Power)*
Power    ::= Unary | UpdateExpr '**' Power
Unary    ::= ('+' | '-' | '!' | '~' | 'void') Unary | UpdateExpr
UpdateExpr ::= Primary | NameUpdate
Primary  ::= Decimal | RadixInt | StringLiteral | 'true' | 'false' | 'null' | Name | Group
Group    ::= '(' Test ')'
Name     ::= [A-Za-z_$] [A-Za-z0-9_$]*  (subject to exclusions below)
Decimal  ::= (Integer ('.' Digits?)? | '.' Digits) Exponent?
Integer  ::= '0' | [1-9] ('_'? [0-9])*
Digits   ::= [0-9] ('_'? [0-9])*
Exponent ::= [eE] [+-]? Digits
RadixInt ::= '0' ([xX] HexDigits | [oO] OctDigits | [bB] BinDigits)
HexDigits ::= [0-9a-fA-F] ('_'? [0-9a-fA-F])*
OctDigits ::= [0-7] ('_'? [0-7])*
BinDigits ::= [01] ('_'? [01])*
```

ECMAScript WhiteSpace, LineTerminator characters, `//` line comments, and `/* ... */` block comments are trivia: they are allowed between tokens and at source boundaries, but cannot join parts of a token. A line comment ends at LF, CR, U+2028 (line separator), U+2029 (paragraph separator), or EOF. A block comment is non-nesting and ends at the first `*/`; EOF before it is a malformed block comment. A line terminator inside a block comment counts as a line break between the surrounding tokens, including for the postfix and jump-target restrictions, but does not cause semicolon insertion.

From tightest to loosest, precedence is name updates `++ --`, prefix `+ - ! ~ void`, exponentiation `**`, multiplicative `* / %`, additive `+ -`, shifts `<< >> >>>`, relational `< <= > >=`, equality `== != === !==`, bitwise `&`, bitwise `^`, bitwise `|`, logical `&&`, logical `||`, then conditional `?:`, then comma `,` (see below for `??`). Prefix operators and `**` associate to the right; other binary operators associate to the left. A bare unary expression cannot be the base of `**`: `-2 ** 2` and `void 2 ** 2` are malformed at `**`, while `(-2) ** 2`, `-(2 ** 2)`, and `2 ** -2` are valid. In an expression, `++x ** 2` and `x++ ** 2` are both valid, but `-++x ** 2` and `-x++ ** 2` need grouping around the base or around the power. `2 ** 3 ** 2` means `2 ** (3 ** 2)`. For example, `1 + 1 << 3` means `(1 + 1) << 3`, `2 & 1 === 0` means `2 & (1 === 0)`, `true == 1 === true` means `(true == 1) === true`, and `3 < 2 < 1` compares the Boolean result of `3 < 2` with `1`, not two relations between the original operands. The conditional operator `?:` binds less tightly than all of these operators and associates to the right: `a ? b : c ? d : e` means `a ? b : (c ? d : e)`. Both arms are parsed and checked against the same subset, but at evaluation time only the selected arm runs. `ToBoolean` leaves Booleans unchanged and maps `null`, `undefined`, the empty String, and Numbers `+0`, `-0`, and NaN to false. Nonempty Strings (even a single NUL or lone surrogate) and all other Numbers (including both infinities) are truthy. The result is the selected arm's value without coercion. A single `/` not starting a comment or longer punctuator is division only after an operand; regular expression literals are outside the slice. The lexer takes the longest match for these operator families: `==`, `!=`, `===`, and `!==` are single comparison tokens, distinct from simple assignment `=`, prefix `!`, and the unsupported arrow `=>` (`==>` tokenizes as `==` followed by `>`); `&&` and `||` are distinct from `&` and `|`; and `<<`, `>>`, and `>>>` are distinct from relational tokens. Each compound assignment operator is one token, distinct from its binary operator. The lexer takes `++` and `--` as single tokens, distinct from `+`, `-`, `+=`, and `-=`. For example, `(x+++1)` is `(x++ + 1)`, not `(x + +1)`. The `*` family takes the longest match among `**=`, `**`, `*=`, and `*`; `2***3` is a power operator followed by an unexpected `*`. Unsupported punctuators such as `=>` and `?.` are rejected as whole punctuators.

The comma operator associates to the left. It evaluates its operands from left to right, discards every intermediate value without coercion, and returns the last value with its original tag. Sequences are allowed in the final expression, in expression statements and statements starting with an assignment or name update, in parenthesized expressions, in `if`, `else if`, `while`, `do`–`while`, and `for` tests, and in nondeclaration `for` initializer and update clauses. A declarator's initializer, an assignment RHS (standalone or grouped), and each arm of `?:` use `Rhs`; a sequence in any of those positions requires grouping parentheses. For example, `true ? 1 : 2, null` evaluates the complete conditional and then returns `null`; `true ? 1, 2 : 3` is malformed, and `true ? (1, 2) : 3` returns `2`. In `const x = (1, 2), y = x; y`, the first comma is an operator, the second separates declarators, and the result is `2`.

A value-producing assignment can start an expression group, with or without later comma operands. A lexical initializer, the RHS of a standalone or grouped assignment, either arm of `?:`, a control statement's test, or a noninitial operand of a comma sequence can start with one or more `Name AssignOp` prefixes, mixing simple `=` with any supported eager or logical compound. Each target must resolve to an initialized `let`, even in skipped code. Simple `=` evaluates the right-hand side once, stores that tagged value, and returns the same value without coercion (except that the outermost standalone store consumes it). Chains associate to the right: `let x; let y; (x = y = null)` stores `null` in `y` before `x` and yields `Value::Null`. The conditional binds tighter than assignment: in `x = test ? y = a : z = b`, the selected arm writes to `y` or `z` and the arms join before the outer store to `x`. In a declaration like `let v = x = test ? y = a : z = b, w = 4;`, the comma starts the next declarator after the conditional joins, `x` is stored, and `v` is initialized. An eager compound loads the old target value once before evaluating the RHS, applies the corresponding binary operator with its usual coercions, and stores and yields its Number result. In `let x = 8; const result = x /= x = 2; result`, the division uses the saved `8` and the RHS result `2`, so the outer assignment stores and yields `4`.

A value-producing logical compound also loads the old target value once. It evaluates the RHS once, stores it, and yields that exact tagged value if the old value is truthy (`&&=`), falsy (`||=`), or `null` or `undefined` (`??=`), respectively. Otherwise it yields the old value without evaluating the RHS or writing to the binding. For example, `let x = false; 0, x ??= 42` yields `Value::Boolean(false)`, whereas `let x; 0, x ??= null` stores and yields `Value::Null`. The parser still validates the entire RHS, including on skipped paths.

Comma binds looser than assignment. For example, `let x; 0, x = 3, x + 1` stores `3` before evaluating `x + 1`, and `if (true, x = 0) { ... }` stores `0` and tests that value. Only a sequence operator admits the subsequent assignment prefix, not a declarator separator or a comma where grouping is required. An explicit expression group can start with a simple, eager compound, or logical assignment. In `(x += a, b)`, the addition and write finish before the comma discards the assignment value and evaluates `b`. In `(x ||= a, b)`, both the skip and write paths reach that discard, and `b` runs on either path. By contrast, in `(x += (a, b))`, the grouped sequence is the assignment RHS and only its final value `b` is used in the addition. A bare prefix cannot start a generic expression or a unary or binary operator operand. The control test itself admits a bare prefix, as in `if (x ||= fallback) { ... }` or `for (; x -= 1;) { ... }`; no inner group is needed. At the root or in a braced block, a statement starting with `Name AssignOp` selects the consuming assignment form, optionally followed by comma operands, as in `let x = 0, y = 1; x = 3, y += x; y` (result `4`). Just as in a nondeclaration `for` initializer or update clause, the first assignment completes (or skips its store) before the next operand runs. The first assignment leaves no value to discard; subsequent operands evaluate left to right and their values are discarded without coercion, including the last. Parenthesized targets such as `((x) = y)` remain unsupported.

Names are case-sensitive ASCII tokens. `const`, `let`, `if`, `else`, `while`, `for`, `do`, `break`, `continue`, `true`, `false`, `null`, and `void` are recognized only as whole tokens and cannot be used as names (`const0`, `let_`, `if0`, `else$`, `while0`, `for_`, `do$`, `break0`, `continue_`, `true$`, `false0`, `null$`, `void0`, and `void_` are names). Other ECMAScript reserved words and literals, strict-mode reserved words, and Unicode and escaped names are outside this slice. We also exclude `await`, `as`, `async`, `from`, `get`, `of`, `set`, `using`, `eval`, `arguments`, `Infinity`, `NaN`, and `globalThis`. A declaration statement has one or more single-name declarators separated by commas, with no trailing comma. Every `const` item requires an initializer (`const x;` and `const x, y = 1;` are `Malformed` at the first delimiter). Each `let` item can omit its initializer; `let x, y = 42; x` returns `Value::Undefined`. Destructuring and `var` declarations are outside the slice. A statement starting with a name followed by `=` or a supported compound assignment operator selects the assignment statement form, with or without a comma suffix. The target must be a single identifier, not a parenthesized name or property access. Declarations, consuming assignment and update statements, expression statements, `break`, `continue`, and the trailing `while (Test);` of a `do` loop require explicit semicolons. A `for` header always needs both separator semicolons, even if its clauses are omitted. There is no automatic semicolon insertion (ASI).

Each standalone block, braced branch, and loop body has its own lexical scope. A `for` with a `let` or `const` declaration list also has a header scope that contains the initializer, test and update, and encloses the body's distinct scope. The loop's header names are not visible after the statement. A `for` without a declaration list uses the surrounding scope for its clauses, as do all other statement tests (including `else if` and the trailing test of `do`); none use an arm or body scope. Reads and write targets resolve to the nearest declaration of that name in their own or an enclosing scope. A declaration shadows an enclosing name throughout its scope, including before initialization, even if there is no explicit initializer. The parser rejects reads and writes before that binding's initialization as `Unsupported` at the accessed name, including self-reads, reads of later items from earlier initializers, and accesses in skipped branches or unreachable code. It does not fall back to an outer binding. An initialized `let` may be assigned, incremented or decremented. An initialized `const` target is `Unsupported` at the assignment or update operator, even for a logical assignment where JavaScript would skip the store. Names are not visible from sibling scopes or after scope exit. `undefined` is an identifier that block and loop header declarations can shadow, not a reserved word. A `let` or `const` declaration named exactly `undefined` at the Script root is `Malformed` at the name: a classic Script cannot lexically redeclare the non-configurable global property. Only if no declaration resolves does a read of `undefined` produce `Value::Undefined`; this immutable default is not stored in a binding slot. An unbound write to `undefined` or any other unbound access is `Unsupported` at the name. Duplicate declarations in one scope, including items of the same list and mixed `let`/`const` pairs, are `Malformed` at the second name. Disjoint scopes, including all arms of an `if` chain, may reuse names; the braced `for` body can also shadow its header's names. The subset does not implement a runtime temporal dead zone, `ReferenceError` or `TypeError`, or global lookup.

Evaluation initializes declarations and runs assignments in source order along the paths taken. In a list, each item's initializer runs and stores its value before the next item's initializer starts, so `const a = 20, b = a + 22; b` returns `Value::Number(42.0)`. A reached `let` item without an initializer initializes its slot to `Value::Undefined`, independently of any binding named `undefined`. Each reached item initializes its slot again on every entry, rather than retaining the prior entry's value. A body declaration runs again when reached on the next iteration; a `for` header declaration runs again only when execution reenters the `for` statement. Each slot holds a tagged primitive value; assignment may change the type in a `let` slot. An eager compound assignment such as `x += y` or `x **= y` loads the current value of `x` once, evaluates the RHS, applies the corresponding binary operator with its usual coercions, and stores the result into the same slot. A logical assignment also loads the current value once, but evaluates and stores the RHS only if the value is truthy (`&&=`), falsy (`||=`), or `null` or `undefined` (`??=`), respectively. Otherwise it skips both evaluation and the store, preserving the original value. For example, `let x = null; x ??= 42; x` returns `Value::Number(42.0)`, while starting with `false` leaves `Value::Boolean(false)`. Standalone assignments leave no result on the operand stack. Slots are fresh for every evaluation, and neither scripts nor evaluations share binding state. No callbacks, closures, or objects are involved.

`++x`, `--x`, `x++`, and `x--` are operands in expressions, including declarator initializers, assignment RHSs, and control tests such as `if (x++) { ... }`. The target must be a bare name, not a parenthesized name, property, or another update. Every form reads the current value of `x` once, applies the numeric coercion described below, adds or subtracts Number `1`, and stores the new Number in the same `let` slot. In expressions, prefix returns the new Number and postfix returns the old **coerced Number**, including signed zero or NaN. For example, `let x = true; let y = x++; y * 10 + x` returns `Value::Number(12.0)`.

At the root or in a braced body, a leading name update followed by a supported binary operator or `?` starts an ordinary expression. For example, `let x = 2; x++ + 1` returns `Value::Number(3.0)`, `let x = 2; ++x ** 2` returns `Value::Number(9.0)`, and `let x = 2; x++ + 1, null` returns `Value::Null`. A leading update followed immediately by `;` or `,` instead keeps the consuming store form: `let x = 0, y = 0; x++, y += x; y` returns `Value::Number(1.0)`. In that form, the update stores before any suffix operand runs and leaves no value to discard; the suffix operands evaluate left to right and all their values are discarded without coercion. Postfix allows no LineTerminator between the identifier and operator, including inside comments. A line terminator is ordinary trivia between a prefix operator and its identifier, or between a complete update and its continuation or delimiter.

An `if` chain evaluates its parenthesized tests from left to right using the same `ToBoolean` rules as `?:`. It executes only the first arm with a truthy test and skips all later tests and arms. If no test is truthy, it executes the final `else` body if present. All tests and arms are parsed and validated, even if skipped at evaluation time. A `while` statement uses the same truthiness and evaluates its parenthesized test before every iteration, including the first. It executes the body in source order after a truthy result and exits after a falsy result. For example, `let n = 3; let sum = 0; while (n) { sum = sum + n; n = n - 1; } sum` returns `Value::Number(6.0)`.

A `for (Init; Test; Update) { ... }` statement runs its initializer once per entry, before its first test. It runs the body only if the test is truthy, then runs the update and retests. All three clauses can be omitted independently: an absent initializer or update does nothing; an absent test is always true. The initializer may be a `const` or `let` declaration list, just as in a declaration statement: items initialize left to right, every `const` item requires an initializer, `let` items may omit theirs, and a trailing comma is not allowed. Otherwise the initializer, like the update, evaluates a supported expression and discards its result without coercion. It can start with a simple, eager compound, or logical assignment, with or without subsequent comma operands. For example, `let i, n; for (i = 0, n = 2; i < 2; i += 1, n *= 2) {} n` returns `Value::Number(8.0)`. Each comma after a completed assignment starts the next operand; to put a sequence inside the RHS itself, use parentheses, such as `i += (null, 1)`. A leading name update can likewise stand alone or run before later operands, as in `let x = 0, y; for (++x, y = 0; y < 2; x++, ++y) {} x`, which returns `Value::Number(3.0)`. When followed immediately by a comma or its clause delimiter (`;` for the initializer, `)` for the updater), the leading update finishes its store without producing a value to discard; subsequent operands use ordinary expression rules and their values are discarded. Before a supported binary operator or `?`, the leading update instead supplies its value to an ordinary discarded expression. For example, `let x = 0, y = 0; for (++x + 0; y < 2; x++ + 1, ++y) {} x` also returns `Value::Number(3.0)`. `continue` reaches the entire update clause, and `break` skips it. A write to a header `const` is rejected even in a skipped update or body. For example, `let i = 0; let sum = 0; for (const step = 2, end = step + 3; i < end; i += step) { sum += i; } sum` updates the surrounding `i` and returns `Value::Number(6.0)`. Declarations in the update, `var` in headers, and `for-in`/`for-of` are outside the slice. The header's fixed slots suffice for this closure-free subset; they do not implement the distinct per-iteration environments that future closures could observe.

A `do { ... } while (Test);` statement runs the body first, even if the test would initially be falsy. After each normal iteration it evaluates the trailing test with the same truthiness rules as `while`: a truthy result restarts the body and a falsy result exits. For example, `let n = 0; do { n += 1; } while (n < 3); n` returns `Value::Number(3.0)`.

Standalone blocks (`{ ... }`) run their statements in source order. They and empty statements (`;`) can appear before the final expression or inside any braced body. Every arm and loop body requires braces. An `else` belongs to the `if` whose then-arm the preceding `}` closed. It may introduce another `if` directly or a final braced body. A semicolon between a then-arm and its `else` ends the statement before the `else`, so the unmatched `else` is rejected. Of the braced control statements, only `do`–`while` takes a trailing semicolon as part of its syntax; a semicolon after any completed block or other control statement is a separate empty statement.

An expression statement is an already-supported `Expr` followed by an explicit `;` and can appear at the root or inside any braced body. When reached, it evaluates the expression and discards the result without coercion. A bare `{` still starts a block; object and function expressions remain unsupported. A consuming assignment or update statement requires an explicit `;` and does not supply the Script result, even if it ends with a comma operand that would be a valid final expression on its own: `let x = 0; x++, x;` still needs a separate final expression. At the root, the required final expression may end with an optional `;` before EOF (ignoring trivia). If another token follows that semicolon, the completed expression is instead a statement and a new final expression is required. Thus `1; 2` returns `2`, `1; /* comment */` returns `1`, and `1;;` is rejected. This is a result rule for the bounded subset, not general JavaScript Script completion.

`break;` exits the innermost enclosing loop and resumes after it, skipping a `for` update or a `do` loop's trailing test. `continue;` skips the rest of that loop body and evaluates its next test using the current bindings, after the update in a `for` (if present). A named `break` may exit a labeled standalone block, `if` chain, or loop, even across intervening blocks, branches, or inner loops. An `if` prefix labels the entire chain: a break to any of its names from any arm resumes after the final arm, skipping the rest of the current arm and all later tests and bodies. For example, `let n = 0; done: { while (true) { n = 42; break done; } n = 1; } n` returns `Value::Number(42.0)`. A named `continue` can target only a labeled loop (`outer: for (...) { ... }`), using the same continue rules as an unlabeled one. Every name in a prefix chain is a break target for the same statement; only a loop's names can also be continue targets. Neither jump produces a result. Prior assignments to still-visible bindings are preserved, but bindings in exited scopes cannot be accessed.

Labels use the same ASCII `Name` syntax and exclusions as binding names but occupy a separate namespace. They neither declare bindings nor introduce scopes. All labels of a block or loop are active in its body, and an `if` chain's labels stay active through its last arm, including in nested statements. The names are available for reuse after the whole target closes. Repeating a name in the same prefix chain or using a name already active on an enclosing statement is `Malformed` at the second name; disjoint statements can reuse a label. An unknown or inactive jump target, or a `continue` naming a block or `if` chain, is `Malformed` at the target name, even in a skipped branch or after another jump. An unlabeled jump without an enclosing loop is `Malformed` at the keyword. A line terminator between a jump keyword and its target, including in a comment, is `Unsupported` at the target name. A semicolon must be written, but may follow a line terminator. Labels on statements other than standalone blocks, braced `if` chains, and braced loops are outside the slice. The parser still checks every block and test, including skipped `for` clauses, code after a jump, and trailing tests skipped by `break`.

A String literal uses matching single or double quotes. Raw Unicode scalars (including NUL, U+2028 and U+2029) are encoded as UTF-16 without normalization; raw CR and LF are malformed. Escapes support escaped quotes and backslash, `\b \f \n \r \t \v`, identity escapes such as `\q`, `\0` not followed by an ASCII decimal digit, `\xHH`, `\uHHHH`, and `\u{...}` with one or more hex digits and a value at most `0x10FFFF` (leading zeros allowed). Unicode escapes preserve lone surrogates. A backslash followed by LF, CR, CRLF, U+2028 or U+2029 is a continuation and adds no code units. Annex B decimal and octal escapes such as `\8` and `\00` are unsupported.

The root directive prologue is the initial run of bare String expression statements, counting an otherwise-final bare literal (with or without `;`). Within that run, exact unescaped `'use strict'` and `"use strict"` are unsupported at the literal span. An escaped spelling is not a Use Strict Directive, though it can be part of the prologue. A group such as `('use strict')`, a continued expression such as `'use strict' || 1`, any statement after the first nondirective statement (even `;`), and statements in nested blocks do not activate strict mode. This does not add ASI: a separator is still required between expressions, and a newline before a continuation operator does not end an expression.

Strings can move through bindings, simple and logical assignment, sequences, and control flow. They are picked or discarded without conversion, including by `void`. Every String is non-nullish. Strict and same-tag loose equality compare exact UTF-16 units. Strict equality across different tags and loose equality between a String and `null` or `undefined` return false. String/Number and String/Boolean loose equality, mixed String/scalar relational comparison, binary `+` (including concatenation), binary `-`, binary bitwise operators, their corresponding eager compounds, and all name updates on Strings report `EvalError::UnsupportedStringOperation` if reached. Skipped expressions still undergo lexical, syntax, and binding checks but do not raise runtime errors.

Unary `+`, `-`, and `~` and binary `*`, `/`, `%`, and `**` (including `*=`, `/=`, `%=`, and `**=`) convert a String to a Number using `StringNumericLiteral`, not the source lexer. It trims precisely ECMAScript WhiteSpace and LineTerminator code units at both ends, without UTF-16 replacement or normalization. Empty or all-whitespace text yields `+0`. A leading ASCII `+` or `-` is permitted on the decimal forms and the exact case-sensitive spelling `Infinity`. Decimal text has one or more ASCII digits, optionally with a point anywhere in that digit sequence (including either end), and optionally an `e`/`E` exponent with an optional ASCII sign and one or more ASCII digits. Decimal leading zeros are allowed. Unsigned `0x`/`0X`, `0o`/`0O`, and `0b`/`0B` require at least one ASCII digit in the specified base and use the same exact integer rounding as source radix literals. Signs on radix forms, numeric separators, internal whitespace, comments, and other unconsumed text are invalid. Invalid numeric text converts to NaN, not a parse error; malformed source quotes or escapes are still rejected while parsing, even in skipped code. Unary `+` returns the converted Number, unary `-` negates it (including either signed zero), and unary `~` applies bitwise NOT to `ToInt32` of the rounded Number. For example, `+' 077 '` is `77`, `+'-1e-999'` is `-0`, `-'-1e-999'` is `+0`, and `~'0xFF'` is `-256`. `+'-0x10'` is NaN and `~'-0x10'` is `-1`, because `ToInt32` maps NaN to zero.

For String decimal magnitudes, this slice uses the pinned Rust `f64` parser to round the full decimal to nearest binary64, ties to even, and applies the sign after rounding to preserve negative zero and underflow. There is no separate exponent scaling, digit truncation or double rounding in this crate. This is our deterministic decimal rounding policy; ECMAScript's `RoundMVResult` permits a choice of endpoint results for decimals with more than 20 significant digits, rather than requiring this implementation strategy. The digit/dot gate excludes Rust-specific `inf`, `NaN`, and case variants; the pinned Rust decimal grammar then checks the entire ASCII magnitude.

A Number literal is one token, with no whitespace or comments inside it. A decimal literal may include a decimal point (`.5`, `1.`, `1.25`), an exponent (`1e3`, `1E-3`), or both (`1.e3`). A sign before the literal is a unary operator; a sign after the decimal exponent marker is part of the exponent. An integer with an explicit `0x`/`0X`, `0o`/`0O`, or `0b`/`0B` prefix requires at least one digit in its base and may have leading zeros after the prefix. It has no fractional or exponent part; `e` and `E` are digits in hexadecimal literals. An out-of-base ASCII decimal digit is malformed at that digit, not split into another token. The `_` separator is allowed only between two digits of the same sequence: decimal integer, fraction, or exponent digits, or digits in an explicit base. For example, `12_345.6_7e-0_2`, `.1_2`, and `0x00_Ff` are supported, but `1__2`, `1_.2`, `1e+_2`, `0x_Ff`, and `0b1_2` are not. Decimal leading-zero forms such as `077`, `08`, and `0_1` remain outside the slice, as do property access, spread, identifier suffixes, and BigInt (including the `n` suffix).

Number literals are rounded directly to binary64 (nearest, ties to even), including positive infinity on overflow and, for decimals, subnormals or positive zero for sufficiently small magnitudes. There is no intermediate rounding or separately rounded scaling. For scalar operands, unary `+` and `-` and binary `+`, `-`, `*`, `/`, `%`, and `**` use `ToNumber` on each operand: Numbers are unchanged, `true` becomes `1`, `false` and `null` become `+0`, and `undefined` becomes NaN. These operators return Numbers and work on binary64, including signed zeros, infinities, and NaN. Binary `+` does not implement concatenation or BigInt arithmetic. Remainder truncates the exact quotient toward zero without rounding it to binary64 first; a zero remainder has the sign of the dividend. For `*`, `/`, `%`, and `**`, both operand expressions run once, left to right, before the operator converts each operand once, also left to right. An eager compound uses the target value saved before the right-hand expression runs: `let x = '8'; x /= (x = '2'); x` yields Number `4`. If a conversion fails, the compound does not store a result; operand expressions already ran.

Exponentiation follows the ECMA-262 Number special cases: a NaN exponent returns NaN; either signed zero exponent returns `1`, even for a NaN base; and any other exponent of a NaN base returns NaN. With an infinite exponent, a base of absolute value `1` returns NaN. Other magnitudes return `+Infinity` if the base magnitude is above `1` and the exponent is positive, or below `1` and the exponent is negative; otherwise they return `+0`. For a finite nonzero exponent, a base of either signed zero gives zero for a positive exponent and infinity for a negative exponent, and an infinite base does the reverse. In those cases the result is negative only for a negative base and an odd integer exponent. A negative finite nonzero base with a finite noninteger exponent returns NaN. For the remaining finite powers Rust's `f64::powf` approximates the magnitude, with a negative sign for a negative base raised to an odd integer. Parity is determined from the represented binary64 Number, not the source digits. The finite approximation is platform-dependent; it is not guaranteed correctly rounded or bit-identical to Node.js.

Number bitwise operators first apply `ToNumber` (scalars for all bitwise operators, and Strings only for unary `~`). `ToUint32` maps NaN, both infinities, and either signed zero to zero; otherwise it truncates the binary64 value toward zero and takes its nonnegative residue modulo 2^32. `ToInt32` interprets those same bits as a signed two's-complement integer. `~`, `&`, `^`, and `|` operate on `ToInt32` operands and return signed 32-bit results as Numbers. `<<` and `>>` use `ToInt32` on the left operand and return signed results (`>>` extends the sign bit); `>>>` uses `ToUint32` on the left and returns an unsigned result, filling with zeros. All three shifts use only the low five bits of `ToUint32` of the right operand. Integer zero results are always Number `+0`. For example, `-1 >> 1` returns `-1`, `-1 >>> 1` returns `2147483647`, and `1 << 33` returns `2`.

Unary `void` evaluates its operand once and replaces its value with `Value::Undefined` without coercion, regardless of any binding named `undefined`. For example, `void 1 ?? 42` means `(void 1) ?? 42` and returns 42, whereas `void (1 ?? 42)` returns `Value::Undefined`. Its operand is parsed and checked even when the whole expression is skipped.

Logical `!` negates `ToBoolean` and returns a Boolean. `&&` preserves a falsy left operand and `||` preserves a truthy left operand; otherwise they evaluate and return the right operand, without coercing the result. `??` preserves a left operand that is neither `null` nor `undefined`; otherwise it evaluates and returns the right operand. Unlike `||`, it preserves `false`, signed zeros, and NaN. The result keeps the selected operand's original tag. `??` binds below all bitwise operators and above `?:`. Mixing `??` with `&&` or `||` in the same test or arm without parentheses is malformed at the second kind of operator. For example, `null ?? false || 7` is malformed, but `(null ?? false) || 7`, `null ?? (false || 7)`, and `true || false ? null ?? 7 : 8` are supported. A logical assignment operator is not part of the RHS expression, so `x ||= null ?? 7` and `x ??= false || 7` are allowed, but `x ||= null ?? false || 7` still requires parentheses within the RHS. Optional chaining is unsupported. Skipped operands and assignment RHSs must still parse, resolve and count toward the prepared instruction ceiling.

Comparisons evaluate both operands from left to right and return a Boolean. Strict equality (`===`) does not coerce its operands: differing tags compare unequal, `null` equals only `null`, `undefined` equals only `undefined`, same-tag Booleans compare by value, and same-tag Numbers compare by binary64 equality (`+0` and `-0` are equal, NaN is unequal to every value including itself, and infinities compare equal only when their signs match). Strict inequality (`!==`) negates that result. Loose equality (`==`, ECMAScript `IsLooselyEqual`) uses strict equality for matching tags. It also equates `null` and `undefined` with each other, but neither is equal to any Number or Boolean. A Number and a Boolean compare numerically after converting `true` to `1` or `false` to `+0`, so `false == -0` is true but `false == null` is false. Loose inequality (`!=`) negates the loose equality result. With scalar operands, the relational operators convert both operands with `ToNumber` and compare them numerically. Signed zeros compare as equal, `-Infinity` is below every finite Number and `+Infinity` is above every finite Number, and all four relational operators return false if either operand is NaN. With two Strings, `<`, `<=`, `>`, and `>=` compare unsigned UTF-16 code units lexicographically, without decoding code points or normalizing. The first differing unit determines the order; if the shared prefix is identical, the shorter String sorts first. The empty String precedes every nonempty String. For example, `'\u{10000}' < '\uE000'` is true because the first unit `0xD800` is less than `0xE000`.

Diagnostics distinguish malformed syntax encountered in this grammar from unsupported input. `Unsupported` does **not** mean the input is valid JavaScript; rejecting an out-of-slice construct does not require validating the rest of it. For example, `1 +`, `(1 + 2`, `1e+`, `-2**3`, and `1/*` are malformed, whereas `1..toString()`, `0_1`, an empty or trivia-only Script, `{}` without a final expression, and `1;;` without a final expression are unsupported. A misplaced `_` in a recognized digit sequence is malformed at the underscore (for example, `1e2_` or `0b1_2`). Both `1 2` and `1/**/2` are malformed; with a line break between the numbers (including inside a block comment), the input is unsupported rather than accepted by automatic semicolon insertion. A successful parse always accounts for the complete source, including any trivia after the final expression. Reads and write targets are resolved after syntactic parsing, so a syntax or resource diagnostic during parsing can precede a binding access diagnostic. Spans are half-open UTF-8 byte ranges. An unterminated block comment spans from its opening delimiter to EOF; errors located at EOF itself use an empty range. Errors do not retain or print source text.

## Bounds and evidence

The default ceilings are 64 KiB of source, 4,096 tokens, a combined expression depth of 128 open parentheses (including the required parentheses of each control header), pending conditional expressions, and pending ungrouped assignment RHSs, and 128 Ki work units. `parse_script_with_limits` takes explicit per-call limits. An additional fixed ceiling allows up to 128 simultaneously active statement frames. Every standalone block and each `if`, `while`, `for`, or `do`–`while` uses one frame, including at the Script root or when a `for` has both a lexical header and a body scope. Prefix labels do not add statement frames or expression nesting. Each `else if` is a nested `if` and uses its own frame, even though the prior arm’s lexical scope has closed. Those frames remain active until the chain ends. A final braced `else` reuses the last `if` frame; empty statements use none. This is independent of the expression limit; exceeding it reports `Limit::NestingDepth` at the next statement's opening brace, control keyword, or first label name.

Tokens include names, declarations, literals, and punctuation but not trivia or EOF. A Boolean or `null` literal consumes one token and contributes its scanned bytes and one instruction emission to the work meter, with no decimal-conversion charge. `undefined` is metered as an ordinary name, including the lexical search before fallback. The work meter charges consumed source bytes (including whitespace and comment delimiters and bodies), decimal normalization and conversion bytes (see below), pushes of pending operators (including comparisons), opening-parenthesis markers (or one unit at the opening parenthesis of a `for` header), conditional arm markers and statement frames, and emitted instructions (including jumps for `?:`, short-circuit operators, and control statements); units are not cycle counts. A statement frame costs one unit at the opening `{` of a standalone block, tested `if` arm, or loop body; a final braced `else` reuses the last `if` frame. A `for` declaration header costs one work unit for its scope at `let`, not another statement frame. Each `if` jump fixup costs one unit: the false edge is patched at `else` or at the tested arm’s closing `}` if there is no `else`; jumps over later arms are patched at the chain’s final `}`. This intentionally raises parse work for existing syntax: an `if` without `else` costs one more unit than before chains were supported, and an `if` with a braced `else` costs two more. The default work ceiling, emitted instructions for existing `if`s, and dispatch accounting are unchanged. An empty statement costs one token and one scanned byte of work. Neither block delimiters nor empty statements emit instructions or incur dispatches. Each `break` and `continue` emits one instruction, with or without a target name.

Each label name and colon consumes a token and is charged for its scanned bytes. After reading the underlying statement's opening brace or control keyword and checking the frame limit, the parser checks labels in prefix order, charging one validation unit per name after the first. Each check searches earlier names of the same prefix (last to first), then active targets (inner to outer). Named jump lookups search only active targets. Each search charges one unit per label visited (last to first within a frame), or one unit for visiting an unlabeled loop; it skips other frames. Each same-length comparison also charges the name's byte length. Validation, visits, and comparisons are charged at the name being checked. Long prefixes can therefore exhaust the work budget before the token budget. A labeled `if` chain enters the target search only once, with its full prefix; its `else if` frames do not incur additional label checks or target visits. Unlabeled `if` chains are skipped by target searches. Work costs for previously supported unlabeled `if` statements and labeled blocks and loops are unchanged. Label syntax adds no instructions or dispatches.

Patching each `break` costs one additional work unit at the target block or loop body's closing `}`, or at the final arm's closing `}` for a labeled `if` chain, after the ordinary `if` fixups. Patching each `continue` targeting a `do` loop still costs one unit at the loop body's closing `}`. Every declarator's duplicate check scans earlier bindings in the same scope, including earlier items in the list. A declarator's comma separator consumes one token and one scanned byte of work; it does not emit an instruction. Each comma operator adds one checked discard instruction (one work unit at the comma and one dispatch when reached). Each expression statement emits the same checked discard for its final value: one work unit at the semicolon, one prepared instruction, and one dispatch when reached. The optional final semicolon does not emit a discard. Sequences need no pending operator or nesting of their own. After syntactic parsing, the resolver visits recorded accesses in source order. It searches the access's own scope and follows parent links outward until it finds a match or runs out of scopes. Within each scope the search visits declarations in reverse declaration order. The work meter charges one unit per candidate visited and one per hop to a parent scope; a same-length name comparison first charges the name's byte length. Sibling scopes are never searched. Many declarations or nested accesses can exhaust the work budget even when source and token limits are not reached. The one-token lookahead after a candidate label name, another statement-start name, an identifier operand, the semicolon ending a root expression, or a tested `if` arm uses the same lexer and preserves the token's span and preceding line-break flag without rescanning or recharging it. Finite lookahead, amortized vector growth and bounded conversion keep the other work bounded.

A decimal literal with a point or exponent has a fixed inclusive ceiling of 4,096 source bytes per literal (`Limit::DecimalLiteralBytes`), including separators, the point, the exponent marker and any exponent sign, but not a preceding unary operator. A decimal integer with 310 or more significant digits (not counting separators) is at least `10^309` and necessarily rounds to infinity. The lexer still validates its entire lexeme and boundary before using that shortcut; the shortcut does not apply to decimals with a point or exponent. All other decimal literals use Rust's `f64` parser, charged by the byte length of its input. If the decimal contains separators, the parser additionally charges one unit per original literal byte for the stripping pass, then fallibly reserves a temporary buffer for exactly the stripped byte length (`Limit::Allocation` if reservation fails). Both charges precede allocation; the buffer is discarded after conversion. Without separators the parser uses the original slice directly.

Prefixed integers have no separate per-literal byte ceiling. They consume one token, one work unit per scanned byte (including the prefix and separators), and one unit to emit the literal instruction. They accumulate digits as they are scanned, using fixed-size state and constant work per digit. The scanner checks separators without feeding them to the accumulator, so there is no stripping buffer or separate conversion charge. Each digit appends 1, 3, or 4 bits. After ignoring leading zeros, conversion retains the first 53 bits, a guard bit, and the OR of all remaining bits (sticky). A guard of zero is below a midpoint; a guard of one with sticky is above it; a guard of one without sticky ties and rounds to the even significand. Carry out of the retained significand advances the exponent, including to infinity at the overflow midpoint `2^1024 - 2^970`. The bit count saturates at 1025 because any larger-than-1024-bit integer is at least `2^1024`; even then the lexer continues charging and validating digits and the token boundary.

A String literal consumes one token, one work unit per scanned source byte (including quotes and escapes), one per emitted UTF-16 unit, and one for its literal instruction. Each literal has an inclusive 4,096-source-byte ceiling (`Limit::StringLiteralBytes`, at the first complete scalar that would cross it, even inside a malformed escape). All literals together have an inclusive 16,384-unit ceiling (`Limit::StringLiteralUnits`, at the scalar or escape that would cross it), including on skipped paths. Both limits are fixed, independent of `Limits`. The parser checks them before consuming the over-limit scalar or appending the over-limit units; it grows the pool with fallible reserve requests capped at the unit ceiling. The resulting Script owns only decoded units in a single immutable pool, not the source. Literal instructions, stack operands, and slots carry a private four-byte range, checked against the pool at literal dispatch, comparison and return. There is no interning or runtime String allocation. On the pinned aarch64 macOS toolchain, `Script` grew from 40 to 64 bytes (one `Vec`, allocation-free without decoded units); instruction, VM operand, and binding-slot sizes stayed 16, 16, and 32 bytes respectively, with optional slots also at 32 bytes. These are measurements, not layout guarantees.

Parsing, evaluation and artifact destruction are iterative, not recursive. Apart from the bounded decimal stripping buffer and String pool, scratch storage and output are proportional to the token count; vector growth is fallible. The parser records one scope per block, one per `for` header with `let`, and one for the Script root, plus one entry per declarator (at least a name and delimiter token and two emitted instructions each), and one site per name read or write. Each arm of an `if` chain gets a distinct scope with the same enclosing scope as its parent. Control headers record their access sites before their body scope opens; a `do` loop’s trailing test records them after its body scope closes. The resolver chooses the lexical binding before checking source order: the access must follow the declarator's comma or terminating semicolon. Only then does it check mutability for writes and patch the instruction's operand. A compound assignment or consuming update target resolves once and patches both the load and store to the same slot. A consuming update emits exactly four instructions, whether or not a comma follows it: load, push Number `1`, add or subtract, and store. Only the suffix's values need discard instructions. An expression update resolves its target once and patches one instruction, charged at the name. That instruction checks the initialized mutable slot, reads and coerces its value once, writes the new Number, and pushes one Number above any existing operands. An update adds no nesting or pending operator of its own. Each instruction counts as one emission and one dispatch when executed; there is no source literal to convert and no trivia rescan. A compound assignment, in addition to the RHS instructions and checked store, emits one load and either a binary instruction (eager) or a checked forward branch (logical). Both are charged as instruction emissions. The eager load stays below the RHS operands until the binary instruction runs. A standalone logical assignment's branch consumes the sole test operand on either path and targets the empty-stack join just after the store. Each declaration has a distinct numeric slot assigned in source order. Each resolved lexical read, assignment, and initializer carries that slot index; an unbound read of `undefined` is patched to a primitive push instead. The private instruction sequence retains no source text, names, or scope metadata. Initialization consumes the sole operand and sets or replaces the designated slot with the declaration's mutability. A `let` without an initializer emits an `Undefined` push followed by the same checked slot initializer used for explicit initializers. Both emissions charge one work unit at the declarator's comma or semicolon and both count toward the prepared instruction ceiling. There is no synthetic token, name lookup, or conversion charge. Each instruction costs one dispatch on a reached path and none on a skipped path. An assignment either stores the RHS value (simple or taken logical assignment), stores the binary result (eager compound assignment), or skips the store (untaken logical assignment). A standalone assignment always leaves the operand stack empty. The parser checks operands and expression stack balance. Tests for `?:`, `if`, and all supported loops are popped by a conditional forward jump with an absolute instruction index (one-past-end denotes exit). The parser patches each forward jump once, through a checked instruction index, to the current emission frontier. A stored frame index finds the innermost loop in constant time; closing a loop restores the index of its enclosing loop. Named jumps and duplicate-label checks follow a separate chain of active target frames outward, comparing spans in the original source. A single fallibly grown scratch vector holds one span per active or pending label, bounded by the consumed name/colon pairs. Each target frame marks its slice's start; closing it truncates the span vector back to that start without a per-label walk. Aliases share the underlying frame and its list of pending breaks threaded through jump operands; a `do` loop also keeps a single list for pending continues. Patching visits each pending jump once without target searches or extra per-jump allocations. For `&&`, `||`, and `??`, a taken forward edge keeps the left value and skips the right operand. The fallthrough path instead drops the left value; the right operand restores the same depth at the join. For `?:`, both arms start at the same post-test stack depth and each adds exactly one value at the join. The statement test consumes the sole operand, leaving an empty stack on either path. An expression statement similarly leaves the stack empty by discarding the sole result after any expression-level branches rejoin. The parser checks for an empty operand stack and no pending expression at statement entry and at block close, including in nested blocks. For each `if` test, the conditional jump skips to the next test, the final `else`, or the common join. Each tested arm with an alternate ends in a forward jump directly to the common join. Closing the chain iteratively pops its pending frames, patching each join jump once in linear time without intermediate jumps or scans. Only the first `if` frame carries the chain's label spans and pending break list. It retains them while each arm's lexical scope closes, then releases the spans and patches each break directly to the same empty-stack join. A break to a labeled standalone block joins at its closing brace's emission frontier without a separate exit instruction. For each loop, the conditional exit and every `break` go just past the loop's final back edge. In `while` and `for`, a dedicated backward instruction at `continue` or at the end of the body targets the start of the loop's update or, if it has none, the start of its test. In a `do` loop, the parser emits the body first and patches continues to the start of the trailing test. The test's forward jump exits on a falsy result; otherwise a back edge returns to the start of the body. A `for` with an update emits it between the test and the body: a forward statement jump skips the update on entry to the body, and a back edge after the update returns to the test. The initializer is emitted before the test and is never the target of a loop back edge. An omitted test emits a true literal followed by the same conditional jump as an explicit test. Emission requires an empty operand stack at unconditional statement jumps and a strictly backward target for each back edge. Peak operand depth accounts for all paths without accumulating across iterations. Prefix and `**` chains use the token and work budgets, not the nesting budget. Each `**` consumes one token and charges for two scanned bytes, one pending operator push, and one checked binary emission. `**=` consumes one token and charges for three scanned bytes before the ordinary eager compound-assignment work. Both use a single exponentiation dispatch when reached, in addition to dispatches for operands and, for `**=`, the target load and store. Each `void` consumes one token and charges for the scanned keyword bytes, one pending operator push and one checked unary emission. It costs one dispatch when reached, in addition to the normal work and dispatches for its operand. A successful parse does not execute initializers, assignments, or any expressions.

The parser charges one work unit at an identifier operand before lookahead: it covers emitting a read or postfix update, attaching an assignment to a group marker, or recording an ungrouped assignment target. A value-producing assignment records a single deferred write site before any RHS accesses. It emits a load at the name for either kind of compound; the load and store are patched together by the single target lookup. An eager compound saves the loaded operand below the RHS. A logical compound emits a checked short-circuit branch at the assignment operator. The branch keeps the loaded operand only on the skip edge; otherwise it drops it before the RHS runs. After RHS operators and branches have joined, the parser verifies that the RHS added exactly one operand. It emits a binary instruction at the operator for an eager compound, then one checked store-keep at the delimiter. A logical branch skips to the very next instruction after that store, which can be a ternary arm's closing jump, an outer assignment's binary operation or store, or a sequence discard. Both paths leave one value above the surrounding operands. Each emission charges one work unit and each reached instruction costs one dispatch. Store-keep requires an available operand and an initialized mutable slot. It copies the top tagged value (the RHS for `=` or a taken logical compound, the binary result for an eager compound) without popping or pushing operands. It leaves preceding operands alone and does not increase peak stack depth.

Each ungrouped `Name AssignOp` prefix uses one pending record with one nesting slot and one work unit charged at the operator, in addition to the identifier charge, normal scanned bytes, instruction emissions and deferred name lookup. At the RHS delimiter, the parser reduces the pending markers inside out, emitting the assignment tails from right to left. Assignments within an arm finish before their conditional joins (at `:` for the consequent); assignments around a conditional RHS finish after that conditional joins. A simple chain adds no operand depth beyond its RHS. An outermost assignment at the start of a group reuses the group record and nesting slot. Its RHS ends at the group's first comma or closing `)`; the group itself remains open until `)`. Ending that assignment at a comma adds no marker push or work charge beyond the usual sequence costs. A standalone outer assignment still emits a consuming store without adding a pending record. The work charges for simple chains, grouped assignments and standalone stores are unchanged. In a control test, the assignment links finish at the test's comma or closing delimiter (`)` or the second `;` in a `for` header). A comma discards the completed result and a statement branch consumes the final test value; neither leaves a result on the statement path.

No slot is cleared when control leaves a block. In a prepared Script, every reference points to the nearest declaration, and that declaration's initializer precedes the reference. Statement branches either enter a block at its start or skip it; jumps may leave scopes but cannot enter a suffix of a block from outside it. A `continue` enters the test or update outside the target loop's body scope. The back edge after a truthy `do` test starts a new entry at the top of the body, never partway through. Thus a reference to a block binding can be reached only after that binding's initializer executed in the current entry of its declaring block; a jump skipping initialization also skips all uses for that entry. A `for` header binding's initializer executes on entry to the whole statement, and its slot remains accessible through the test, body and update until the loop exits. Exited slots are inaccessible until initialization on a subsequent entry, so unused or stale slots have no effect.

The evaluator first checks an inclusive ceiling of 4,096 prepared instructions (`EvalError::LimitExceeded`), including skipped paths and their jumps, even when the parser is given higher limits. This bounds temporary storage to at most 2,048 tagged operand slots and 2,047 optional binding slots (each declaration needs at least two instructions and the final expression at least one). Both vectors reserve storage fallibly; bindings start empty and untaken paths can leave them empty. The evaluator checks jump targets, requiring all edges except `LoopBack` to go strictly forward. `LoopBack` must go strictly backward. Both backward and forward unconditional statement jumps require an empty operand stack. A discard requires an operand and removes only the top value. Reads and writes must target initialized slots, initializers must target in-range slots and can replace only a value from the same initializer instruction, and assignments must target mutable slots. Malformed reached instructions are distinct from resource exhaustion (`EvalError::InvalidScript`).

Each evaluation gets a separate fixed budget of 16,384 dispatches. Every dispatched instruction costs one unit, including short-circuit branches, loop tests, `for` initializer and update instructions, `break`, `continue`, and loop back edges. Skipped instructions cost no dispatches, and reaching the end costs none. A script that finishes on dispatch 16,384 succeeds; if it needs another dispatch, evaluation stops before running that instruction and returns `EvalError::DispatchLimitExceeded`. Even `while (true) {}`, `for (;;) {}`, and `do {} while (true);` cost three dispatches per complete iteration (literal, conditional jump, backward jump). The budget and all binding state reset on the next evaluation.

String equality and relational comparisons share a fixed budget of 65,536 code-unit pairs per evaluation. Equality charges the full length for equal-length Strings; different lengths and mixed tags cost no pairs. Ordering between two Strings charges the shorter length, including zero if either String is empty. Both charge before comparing units, even for aliases or an early mismatch. A reached comparison that would exceed the inclusive ceiling fails with `EvalError::StringComparisonLimitExceeded`. Skipped instructions cost no pairs. Each reached comparison costs one dispatch, checked before the comparison runs.

String numeric conversion has a separate inclusive 262,144-credit budget shared by unary `+`, `-`, and `~` and binary `*`, `/`, `%`, and `**` (including their eager compound forms), reset for each evaluation. After charging the operator's single dispatch, checking stack arity, and validating the operand's String range, the evaluator precharges `1 +` the original UTF-16 length, before trimming. Trimmed-empty text, exact optionally signed `Infinity`, and recognized unsigned radix prefixes (even if their digits are invalid) pay only this base charge. Every other candidate pays another `256 + 3 *` the trimmed magnitude length, excluding one optional leading sign. The surcharge is checked before the digit/dot gate, ASCII copy and decimal parser, even for a sign with no magnitude or an invalid first or last unit. Either charge can fail with `EvalError::StringNumericConversionLimitExceeded`. A binary instruction charges each String operand, even when both alias the same range. Untaken instructions, scalar operands, comparisons and other String uses consume no conversion credits. Neither the dispatch budget nor the comparison pair budget can borrow from this meter.

Per-literal source limits imply at most 4,094 decoded units (quotes emit nothing and escapes cannot expand past their source byte count). Conversion works only on the checked prepared UTF-16 slice, without an extra heap allocation or source replay. It uses fixed-size state for radix accumulation, validates digits through overflow, and uses a fixed 4,094-byte stack scratch only on the decimal helper path. The pinned Rust decimal implementation uses fast paths and a fixed-size fallback digit buffer (768 bytes plus bookkeeping and sticky information); that allocation behavior is not a public Rust API guarantee. Credits bound aggregate input and the number of decimal attempts, not native worst-case cycles: at most 64 full-length base-only conversions or 15 full-length decimal attempts fit, and a digit/dot attempt costs at least 261 credits. These limits do not change lexer costs, bytecode, or existing scalar operator costs.

On the pinned `aarch64-apple-darwin` build, observed sizes are 4 bytes for a String range, 16 each for an instruction and operand, and 32 for an optional binding slot. This path adds no fields to any of them. ## Gaps

This is a standalone prototype against ECMA-262, 16th edition (2025), especially its lexical grammar, decimal and explicitly prefixed Number literals, Boolean, `null`, and ordinary String literals, `ToBoolean` of primitives, `ToNumber` of scalars and bounded String coercion in unary `+`, `-`, and `~` and binary `*`, `/`, `%`, and `**` (including their eager compounds), `ToInt32` and `ToUint32`, Number bitwise operations and exponentiation, strict and loose equality and relational comparison for those values, and expression grammar. It does not implement general Script or Module syntax or their full early-error rules, ASI, value types other than Number, Boolean, Null, Undefined and String (including BigInt, Symbols, and objects), general directive semantics, template literals, other String coercions, concatenation, indexing, properties, wrappers and String built-ins, other coercions, the browser `IsHTMLDDA` equality exception, other unary or binary operators, calls, host hooks, general expression statements, a runtime temporal dead zone, unbraced control bodies, labels on statements other than standalone blocks, braced `if` chains and braced loops, `switch`, general global lookup or writes, optional chaining, other declaration forms, other loop forms (including `for-in` and `for-of`), assignment expressions beyond bare-name prefixes in groups, initializers, assignment RHSs, conditional arms, control tests, classic `for` expression clauses, or noninitial sequence operands, expression-valued increment/decrement on anything other than a bare name, property targets, regular expression literals, hashbang comments or Annex B behavior (including HTML-like comments), alternate numeric literal syntax or JavaScript source represented as arbitrary UTF-16 code units. It does not implement host cancellation, general JavaScript execution, or renderer integration. Allocator, toolchain and platform behavior are outside the parser's guarantees.
