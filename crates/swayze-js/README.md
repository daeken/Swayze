## Supported slice

`parse_script` parses a JavaScript Script with zero or more `const` or `let` declaration statements (with one or more single-name declarators), assignments, standalone increments and decrements, bare blocks, empty statements, and braced `if`, `while`, `for`, and `do`–`while` statements in source order, followed by one required expression. Call `Script::evaluate_value` for the final expression's `Value::Number(f64)`, `Value::Boolean(bool)`, `Value::Null`, or `Value::Undefined`. For example, `let x = 0; if (true) { const answer = 42; x = answer; } else { x = 2; } x` returns `Value::Number(42.0)`. The compatibility method `Script::evaluate` returns a Number as `f64` and reports `EvalError::NonNumericResult` for any other result without converting it. The error variant is unchanged; its message is now `script result is not a Number`. `prepare` is still an unsupported compatibility shim.

`Value`'s Rust `PartialEq` compares matching variants and their payloads; `f64` equality treats signed zeros as equal and NaN as unequal to itself. This is a host-side convenience, not a definition of guest JavaScript equality.

```text
Script   ::= Stmt* Expr ';'? EOF
Stmt     ::= Decl | Write | Block | Empty | If | While | For | DoWhile | LoopJump
Empty    ::= ';'
Decl     ::= 'const' ConstItem (',' ConstItem)* ';' | 'let' LetItem (',' LetItem)* ';'
ConstItem ::= Name '=' Expr
LetItem   ::= Name ('=' Expr)?
Write    ::= Store ';'
Store    ::= Name AssignOp Expr | Update
Update   ::= UpdateOp Name | Name [no LineTerminator here] UpdateOp
UpdateOp ::= '++' | '--'
AssignOp ::= '=' | '+=' | '-=' | '*=' | '/=' | '%=' | '&=' | '^=' | '|=' | '<<=' | '>>=' | '>>>='
           | '&&=' | '||=' | '??='
If       ::= 'if' '(' Expr ')' Block ('else' Block)?
While    ::= 'while' '(' Expr ')' Block
For      ::= 'for' '(' Store? ';' Expr? ';' Store? ')' Block
DoWhile  ::= 'do' Block 'while' '(' Expr ')' ';'
Block    ::= '{' Stmt* '}'
LoopJump ::= ('break' | 'continue') ';'  (requires an enclosing While, For, or DoWhile)
Expr     ::= (Or | Coalesce) ('?' Expr ':' Expr)?
Or       ::= And ('||' And)*
Coalesce ::= BitOr ('??' BitOr)+
And      ::= BitOr ('&&' BitOr)*
BitOr    ::= BitXor ('|' BitXor)*
BitXor   ::= BitAnd ('^' BitAnd)*
BitAnd   ::= Equality ('&' Equality)*
Equality ::= Relation (('==' | '!=' | '===' | '!==') Relation)*
Relation ::= Shift (('<' | '<=' | '>' | '>=') Shift)*
Shift    ::= Sum (('<<' | '>>' | '>>>') Sum)*
Sum      ::= Product (('+' | '-') Product)*
Product  ::= Unary (('*' | '/' | '%') Unary)*
Unary    ::= ('+' | '-' | '!' | '~') Unary | Primary
Primary  ::= Decimal | RadixInt | 'true' | 'false' | 'null' | Name | '(' Expr ')'
Name     ::= [A-Za-z_$] [A-Za-z0-9_$]*  (subject to exclusions below)
Decimal  ::= (Integer ('.' Digits?)? | '.' Digits) Exponent?
Integer  ::= '0' | [1-9] ('_'? [0-9])*
Digits   ::= [0-9] ('_'? [0-9])*
Exponent ::= [eE] [+-]? Digits
RadixInt ::= '0' ([xX] HexDigits | [oO] OctDigits | [bB] BinDigits)
HexDigits ::= [0-9a-fA-F] ('_'? [0-9a-fA-F])*
OctDigits ::= [0-7] ('_'? [0-7])*
BinDigits ::= [01] ('_'? [01])*
```

ECMAScript WhiteSpace, LineTerminator characters, `//` line comments, and `/* ... */` block comments are trivia: they are allowed between tokens and at source boundaries, but cannot join parts of a token. A line comment ends at LF, CR, U+2028 (line separator), U+2029 (paragraph separator), or EOF. A block comment is non-nesting and ends at the first `*/`; EOF before it is a malformed block comment. A line terminator inside a block comment counts as a line break between the surrounding tokens, including for the postfix restriction and diagnostics, but does not cause semicolon insertion.

From tightest to loosest, precedence is prefix `+ - ! ~`, multiplicative `* / %`, additive `+ -`, shifts `<< >> >>>`, relational `< <= > >=`, equality `== != === !==`, bitwise `&`, bitwise `^`, bitwise `|`, logical `&&`, logical `||`, then conditional `?:` (see below for `??`). Prefix operators associate to the right and binary operators associate to the left. For example, `1 + 1 << 3` means `(1 + 1) << 3`, `2 & 1 === 0` means `2 & (1 === 0)`, `true == 1 === true` means `(true == 1) === true`, and `3 < 2 < 1` compares the Boolean result of `3 < 2` with `1`, not two relations between the original operands. The conditional operator `?:` binds less tightly than all of these operators and associates to the right: `a ? b : c ? d : e` means `a ? b : (c ? d : e)`. Both arms are parsed and checked against the same subset, but at evaluation time only the selected arm runs. `ToBoolean` leaves Booleans unchanged and maps `null`, `undefined`, and Numbers `+0`, `-0`, and NaN to false, all other Numbers (including both infinities) to true. The result is the selected arm's value without coercion. A single `/` not starting a comment or longer punctuator is division only after an operand; regular expression literals are outside the slice. The lexer takes the longest match for these operator families: `==`, `!=`, `===`, and `!==` are single comparison tokens, distinct from simple assignment `=`, prefix `!`, and the unsupported arrow `=>` (`==>` tokenizes as `==` followed by `>`); `&&` and `||` are distinct from `&` and `|`; and `<<`, `>>`, and `>>>` are distinct from relational tokens. Each compound assignment operator is one token, distinct from its binary operator. The lexer takes `++` and `--` as single tokens, distinct from `+`, `-`, `+=`, and `-=`. For example, `x+++1` begins with `x` and `++`, not `x` and `+`; unlike `x + +1`, it is outside the slice. Unsupported punctuators such as `=>`, `**`, `**=`, and `?.` are rejected as whole punctuators.

Names are case-sensitive ASCII tokens. `const`, `let`, `if`, `else`, `while`, `for`, `do`, `break`, `continue`, `true`, `false`, and `null` are recognized only as whole tokens and cannot be used as names (`const0`, `let_`, `if0`, `else$`, `while0`, `for_`, `do$`, `break0`, `continue_`, `true$`, `false0`, and `null$` are names). Other ECMAScript reserved words and literals, strict-mode reserved words, and Unicode and escaped names are outside this slice. We also exclude `await`, `as`, `async`, `from`, `get`, `of`, `set`, `using`, `eval`, `arguments`, `Infinity`, `NaN`, and `globalThis`. A declaration statement has one or more single-name declarators separated by commas, with no trailing comma. Every `const` item requires an initializer (`const x;` and `const x, y = 1;` are `Malformed` at the first delimiter). Each `let` item can omit its initializer; `let x, y = 42; x` returns `Value::Undefined`. Destructuring, `var` declarations, and comma expressions (even parenthesized in an initializer) are outside the slice. A statement starting with a name followed by `=` or a supported compound assignment operator is an assignment, not an expression. The target must be a single identifier, not a parenthesized name or property access. Declarations, assignments, standalone increments and decrements, `break`, `continue`, and the trailing `while (Expr);` of a `do` loop require explicit semicolons. A `for` header always needs both separator semicolons, even if its clauses are omitted. The final expression's semicolon is optional. There is no automatic semicolon insertion (ASI).

Each bare block, braced branch, and loop body has its own lexical scope. The test (including a `do` loop’s trailing test) and all `for` header clauses are in the enclosing scope, not in the new block. Reads and write targets resolve to the nearest declaration of that name in their own or an enclosing scope. A declaration shadows an enclosing name throughout its block, including before initialization, even if there is no explicit initializer. The parser rejects reads and writes before that binding's initialization as `Unsupported` at the accessed name, including self-reads, reads of later items from earlier initializers, and accesses in skipped branches or unreachable code. It does not fall back to an outer binding. An initialized `let` may be assigned, incremented or decremented. An initialized `const` target is `Unsupported` at the assignment or update operator, even for a logical assignment where JavaScript would skip the store. Block names are not visible from sibling blocks or after scope exit. `undefined` is an identifier that block declarations can shadow, not a reserved word. A `let` or `const` declaration named exactly `undefined` at the Script root is `Malformed` at the name: a classic Script cannot lexically redeclare the non-configurable global property. Only if no declaration resolves does a read of `undefined` produce `Value::Undefined`; this immutable default is not stored in a binding slot. An unbound write to `undefined` or any other unbound access is `Unsupported` at the name. Duplicate declarations in one scope, including items of the same list and mixed `let`/`const` pairs, are `Malformed` at the second name. Disjoint blocks, including then/else arms, may reuse names. The subset does not implement a runtime temporal dead zone, `ReferenceError` or `TypeError`, or global lookup.

Evaluation initializes declarations and runs assignments in source order along the paths taken. In a list, each item's initializer runs and stores its value before the next item's initializer starts, so `const a = 20, b = a + 22; b` returns `Value::Number(42.0)`. A reached `let` item without an initializer initializes its slot to `Value::Undefined`, independently of any binding named `undefined`. Each reached item initializes its slot again on every entry, including on repeated iterations, rather than retaining the prior entry's value. Each slot holds a tagged primitive value; assignment may change the type in a `let` slot. An eager compound assignment such as `x += y` loads the current value of `x` once, evaluates the RHS, applies the corresponding binary operator with its usual coercions, and stores the result into the same slot. A logical assignment also loads the current value once, but evaluates and stores the RHS only if the value is truthy (`&&=`), falsy (`||=`), or `null` or `undefined` (`??=`), respectively. Otherwise it skips both evaluation and the store, preserving the original value. For example, `let x = null; x ??= 42; x` returns `Value::Number(42.0)`, while starting with `false` leaves `Value::Boolean(false)`. No assignment leaves a result on the operand stack. Slots are fresh for every evaluation, and neither scripts nor evaluations share binding state. No callbacks, closures, or objects are involved.

`++x`, `--x`, `x++`, and `x--` are supported only as standalone statements and in `for` initializer and update clauses. Both prefix and postfix forms load the current value of `x` once, apply the numeric coercion described below, add or subtract Number `1`, and store the Number in the same `let` slot. They leave no result: neither an old value nor a new value is available to an expression. Postfix allows no LineTerminator between the identifier and operator. For example, `x/**/++;` is allowed, but adding a line terminator inside that comment makes it unsupported. There is no corresponding restriction between a prefix operator and its identifier, or between a complete update and its explicit delimiter.

An `if` statement evaluates its parenthesized test using the same `ToBoolean` rules as `?:` and executes only the selected branch. A falsy test without `else`, or a selected empty branch, performs no writes. A `while` statement uses the same truthiness and evaluates its parenthesized test before every iteration, including the first. It executes the body in source order after a truthy result and exits after a falsy result. For example, `let n = 3; let sum = 0; while (n) { sum = sum + n; n = n - 1; } sum` returns `Value::Number(6.0)`.

A `for (Init; Test; Update) { ... }` statement runs its initializer once, before its first test. It runs the body only if the test is truthy, then runs the update and retests. All three clauses can be omitted independently: an absent initializer or update performs no writes; an absent test is always true. The initializer and update, when present, must be simple, eager compound, or logical assignments, or standalone increments or decrements, to already initialized `let` bindings. Declarations, comma expressions, and `for-in`/`for-of` are outside the slice. For example, `let i = 0; let sum = 0; for (++i; i <= 3; i++) { sum += i; } sum` returns `Value::Number(6.0)`.

A `do { ... } while (Test);` statement runs the body first, even if the test would initially be falsy. After each normal iteration it evaluates the trailing test with the same truthiness rules as `while`: a truthy result restarts the body and a falsy result exits. For example, `let n = 0; do { n += 1; } while (n < 3); n` returns `Value::Number(3.0)`.

Bare blocks (`{ ... }`) run their statements in source order. They and empty statements (`;`) can appear before the final expression or inside any braced body. Every branch and loop body still requires braces. An `else` belongs to the `if` whose then-arm the preceding `}` closed; an `else` may contain a nested `if` only inside its own braces. An empty statement between a then-arm and `else` is not allowed. Of the braced control statements, only `do`–`while` takes a trailing semicolon as part of its syntax; a semicolon after any completed block or other control statement is a separate empty statement. General expression statements are outside the slice. No statement replaces the required final expression, and nothing except its optional semicolon and trivia may follow that expression.

`break;` exits the innermost enclosing loop and resumes after it, skipping a `for` update or a `do` loop's trailing test. `continue;` skips the rest of that loop body and evaluates its next test using the current bindings, after the update in a `for` (if present). Intervening bare blocks and `if` branches are not jump targets. Prior assignments to still-visible bindings are preserved, but bindings in exited scopes cannot be accessed. Neither jump produces a result. An unlabeled jump without an enclosing loop is `Malformed` at the keyword, even in an inactive branch. Labels and labeled jumps are unsupported. The parser still checks every block and test, including skipped `for` clauses, code after a jump, and trailing tests skipped by `break`.

A Number literal is one token, with no whitespace or comments inside it. A decimal literal may include a decimal point (`.5`, `1.`, `1.25`), an exponent (`1e3`, `1E-3`), or both (`1.e3`). A sign before the literal is a unary operator; a sign after the decimal exponent marker is part of the exponent. An integer with an explicit `0x`/`0X`, `0o`/`0O`, or `0b`/`0B` prefix requires at least one digit in its base and may have leading zeros after the prefix. It has no fractional or exponent part; `e` and `E` are digits in hexadecimal literals. An out-of-base ASCII decimal digit is malformed at that digit, not split into another token. The `_` separator is allowed only between two digits of the same sequence: decimal integer, fraction, or exponent digits, or digits in an explicit base. For example, `12_345.6_7e-0_2`, `.1_2`, and `0x00_Ff` are supported, but `1__2`, `1_.2`, `1e+_2`, `0x_Ff`, and `0b1_2` are not. Decimal leading-zero forms such as `077`, `08`, and `0_1` remain outside the slice, as do property access, spread, identifier suffixes, and BigInt (including the `n` suffix).

Number literals are rounded directly to binary64 (nearest, ties to even), including positive infinity on overflow and, for decimals, subnormals or positive zero for sufficiently small magnitudes. There is no intermediate rounding or separately rounded scaling. Unary `+` and `-` and binary `+`, `-`, `*`, `/`, and `%` use `ToNumber` on each operand: Numbers are unchanged, `true` becomes `1`, `false` and `null` become `+0`, and `undefined` becomes NaN. These operators return Numbers and work on binary64, including signed zeros, infinities, and NaN. Binary `+` has no string or BigInt cases in this subset. Remainder truncates the exact quotient toward zero without rounding it to binary64 first; a zero remainder has the sign of the dividend.

Number bitwise operators first apply the same `ToNumber` coercion. `ToUint32` maps NaN, both infinities, and either signed zero to zero; otherwise it truncates the binary64 value toward zero and takes its nonnegative residue modulo 2^32. `ToInt32` interprets those same bits as a signed two's-complement integer. `~`, `&`, `^`, and `|` operate on `ToInt32` operands and return signed 32-bit results as Numbers. `<<` and `>>` use `ToInt32` on the left operand and return signed results (`>>` extends the sign bit); `>>>` uses `ToUint32` on the left and returns an unsigned result, filling with zeros. All three shifts use only the low five bits of `ToUint32` of the right operand. Integer zero results are always Number `+0`. For example, `-1 >> 1` returns `-1`, `-1 >>> 1` returns `2147483647`, and `1 << 33` returns `2`.

Logical `!` negates `ToBoolean` and returns a Boolean. `&&` preserves a falsy left operand and `||` preserves a truthy left operand; otherwise they evaluate and return the right operand, without coercing the result. `??` preserves a left operand that is neither `null` nor `undefined`; otherwise it evaluates and returns the right operand. Unlike `||`, it preserves `false`, signed zeros, and NaN. The result keeps the selected operand's original tag. `??` binds below all bitwise operators and above `?:`. Mixing `??` with `&&` or `||` in the same test or arm without parentheses is malformed at the second kind of operator. For example, `null ?? false || 7` is malformed, but `(null ?? false) || 7`, `null ?? (false || 7)`, and `true || false ? null ?? 7 : 8` are supported. A logical assignment operator is not part of the RHS expression, so `x ||= null ?? 7` and `x ??= false || 7` are allowed, but `x ||= null ?? false || 7` still requires parentheses within the RHS. Optional chaining is unsupported. Skipped operands and assignment RHSs must still parse, resolve and count toward the prepared instruction ceiling.

Comparisons evaluate both operands from left to right and return a Boolean. Strict equality (`===`) does not coerce its operands: differing tags compare unequal, `null` equals only `null`, `undefined` equals only `undefined`, same-tag Booleans compare by value, and same-tag Numbers compare by binary64 equality (`+0` and `-0` are equal, NaN is unequal to every value including itself, and infinities compare equal only when their signs match). Strict inequality (`!==`) negates that result. Loose equality (`==`, ECMAScript `IsLooselyEqual`) uses strict equality for matching tags. It also equates `null` and `undefined` with each other, but neither is equal to any Number or Boolean. A Number and a Boolean compare numerically after converting `true` to `1` or `false` to `+0`, so `false == -0` is true but `false == null` is false. Loose inequality (`!=`) negates the loose equality result. The relational operators convert both operands with `ToNumber` and compare them numerically. Signed zeros compare as equal, `-Infinity` is below every finite Number and `+Infinity` is above every finite Number, and all four relational operators return false if either operand is NaN.

Diagnostics distinguish malformed syntax encountered in this grammar from unsupported input. `Unsupported` does **not** mean the input is valid JavaScript; rejecting an out-of-slice construct does not require validating the rest of it. For example, `1 +`, `(1 + 2`, `1e+`, and `1/*` are malformed, whereas `1..toString()`, `0_1`, `2**3`, an empty or trivia-only Script, `{}` without a final expression, and `1; 2` are unsupported. A misplaced `_` in a recognized digit sequence is malformed at the underscore (for example, `1e2_` or `0b1_2`). Both `1 2` and `1/**/2` are malformed; with a line break between the numbers (including inside a block comment), the input is unsupported rather than accepted by automatic semicolon insertion. A successful parse always accounts for the complete source, including anything after the optional semicolon. Reads and write targets are resolved after syntactic parsing, so a syntax or resource diagnostic during parsing can precede a binding access diagnostic. Spans are half-open UTF-8 byte ranges. An unterminated block comment spans from its opening delimiter to EOF; errors located at EOF itself use an empty range. Errors do not retain or print source text.

## Bounds and evidence

The default ceilings are 64 KiB of source, 4,096 tokens, a combined expression depth of 128 open parentheses (including the required parentheses of each control header) and pending conditional expressions, and 128 Ki work units. `parse_script_with_limits` takes explicit per-call limits. An additional fixed ceiling allows up to 128 simultaneously active statement frames. Every bare block and each `if`, `while`, `for`, or `do`–`while` uses one frame, including at the Script root. Both arms of an `if` share one frame; empty statements use none. This is independent of the expression limit; exceeding it reports `Limit::NestingDepth` at the next opening brace of a bare block or at the next control keyword.

Tokens include names, declarations, literals, and punctuation but not trivia or EOF. A Boolean or `null` literal consumes one token and contributes its scanned bytes and one instruction emission to the work meter, with no decimal-conversion charge. `undefined` is metered as an ordinary name, including the lexical search before fallback. The work meter charges consumed source bytes (including whitespace and comment delimiters and bodies), decimal normalization and conversion bytes (see below), pushes of pending operators (including comparisons), opening-parenthesis markers (or one unit at the opening parenthesis of a `for` header), conditional arm markers and statement frames, and emitted instructions (including jumps for `?:`, short-circuit operators, and control statements); units are not cycle counts. A statement frame costs one unit at the opening `{` of a bare block, then-arm, or loop body; an `else` reuses that frame. An empty statement costs one token and one scanned byte of work. Neither bare block delimiters nor empty statements emit instructions or incur dispatches. `break;` and `continue;` each emit one instruction. Patching each `break` and each `continue` in a `do` loop costs one additional unit charged at the owning body's closing `}`. Every declarator's duplicate check scans earlier bindings in the same scope, including earlier items in the list. The comma separator consumes one token and one scanned byte of work; it does not emit an instruction. After syntactic parsing, the resolver visits recorded accesses in source order. It searches the access's own scope and follows parent links outward until it finds a match or runs out of scopes. Within each scope the search visits declarations in reverse declaration order. The work meter charges one unit per candidate visited and one per hop to a parent scope; a same-length name comparison first charges the name's byte length. Sibling scopes are never searched. Many declarations or nested accesses can exhaust the work budget even when source and token limits are not reached. The one-token lookahead after a top-level name or the first branch of an `if` uses the same lexer and preserves the token's span and preceding line-break flag without rescanning or recharging it. Finite lookahead, amortized vector growth and bounded conversion keep the other work bounded.

A decimal literal with a point or exponent has a fixed inclusive ceiling of 4,096 source bytes per literal (`Limit::DecimalLiteralBytes`), including separators, the point, the exponent marker and any exponent sign, but not a preceding unary operator. A decimal integer with 310 or more significant digits (not counting separators) is at least `10^309` and necessarily rounds to infinity. The lexer still validates its entire lexeme and boundary before using that shortcut; the shortcut does not apply to decimals with a point or exponent. All other decimal literals use Rust's `f64` parser, charged by the byte length of its input. If the decimal contains separators, the parser additionally charges one unit per original literal byte for the stripping pass, then fallibly reserves a temporary buffer for exactly the stripped byte length (`Limit::Allocation` if reservation fails). Both charges precede allocation; the buffer is discarded after conversion. Without separators the parser uses the original slice directly.

Prefixed integers have no separate per-literal byte ceiling. They consume one token, one work unit per scanned byte (including the prefix and separators), and one unit to emit the literal instruction. They accumulate digits as they are scanned, using fixed-size state and constant work per digit. The scanner checks separators without feeding them to the accumulator, so there is no stripping buffer or separate conversion charge. Each digit appends 1, 3, or 4 bits. After ignoring leading zeros, conversion retains the first 53 bits, a guard bit, and the OR of all remaining bits (sticky). A guard of zero is below a midpoint; a guard of one with sticky is above it; a guard of one without sticky ties and rounds to the even significand. Carry out of the retained significand advances the exponent, including to infinity at the overflow midpoint `2^1024 - 2^970`. The bit count saturates at 1025 because any larger-than-1024-bit integer is at least `2^1024`; even then the lexer continues charging and validating digits and the token boundary.

Parsing, evaluation and artifact destruction are iterative, not recursive. Apart from the bounded decimal stripping buffer, scratch storage and output are proportional to the token count; vector growth is fallible. The parser records one scope per block plus the Script root, one entry per declarator (at least a name and delimiter token and two emitted instructions each), and one site per name read or write. An `else` reuses its control frame but has a distinct scope with the same parent as the then-arm. Control headers record their access sites before their body scope opens; a `do` loop’s trailing test records them after its body scope closes. The resolver chooses the lexical binding before checking source order: the access must follow the declarator's comma or terminating semicolon. Only then does it check mutability for writes and patch the instruction's operand. A compound assignment or update target resolves once and patches both the load and store to the same slot. An update emits exactly four instructions: load, push Number `1`, add or subtract, and store. Each counts as one emission and one dispatch when executed; there is no source literal to convert and no trivia rescan. A compound assignment, in addition to the RHS instructions and checked store, emits one load and either a binary instruction (eager) or a checked forward branch (logical). Both are charged as instruction emissions. The eager load stays below the RHS operands until the binary instruction runs. The logical branch consumes the sole test operand on either path and targets the empty-stack join just after the store. Each declaration has a distinct numeric slot assigned in source order. Each resolved lexical read, assignment, and initializer carries that slot index; an unbound read of `undefined` is patched to a primitive push instead. The private instruction sequence retains no source text, names, or scope metadata. Initialization consumes the sole operand and sets or replaces the designated slot with the declaration's mutability. A `let` without an initializer emits an `Undefined` push followed by the same checked slot initializer used for explicit initializers. Both emissions charge one work unit at the declarator's comma or semicolon and both count toward the prepared instruction ceiling. There is no synthetic token, name lookup, or conversion charge. Each instruction costs one dispatch on a reached path and none on a skipped path. An assignment either stores the RHS value (simple or taken logical assignment), stores the binary result (eager compound assignment), or skips the store (untaken logical assignment). It always leaves the operand stack empty. The parser checks operands and expression stack balance. Tests for `?:`, `if`, and all supported loops are popped by a conditional forward jump with an absolute instruction index (one-past-end denotes exit). The parser patches each forward jump once, through a checked instruction index, to the current emission frontier. A stored frame index finds the innermost loop in constant time; closing a loop restores the index of its enclosing loop. Each loop links its pending breaks through the jump operands; a `do` loop keeps a separate list for pending continues. Patching visits each pending jump once without target searches or extra per-jump allocations. For `&&`, `||`, and `??`, a taken forward edge keeps the left value and skips the right operand. The fallthrough path instead drops the left value; the right operand restores the same depth at the join. For `?:`, both arms start at the same post-test stack depth and each adds exactly one value at the join. The statement form consumes the sole operand, leaving an empty stack on either path. The parser checks for an empty operand stack and no pending expression at statement entry and at block close, including in nested blocks. For `if`, the conditional jump skips to `else` if present or directly to the join otherwise. When `else` is present, a second forward jump skips it after the true branch. For each loop, the conditional exit and every `break` go just past the loop's final back edge. In `while` and `for`, a dedicated backward instruction at `continue` or at the end of the body targets the start of the loop's update or, if it has none, the start of its test. In a `do` loop, the parser emits the body first and patches continues to the start of the trailing test. The test's forward jump exits on a falsy result; otherwise a back edge returns to the start of the body. A `for` with an update emits it between the test and the body: a forward statement jump skips the update on entry to the body, and a back edge after the update returns to the test. The initializer is emitted before the test and is never the target of a loop back edge. An omitted test emits a true literal followed by the same conditional jump as an explicit test. Emission requires an empty operand stack at unconditional statement jumps and a strictly backward target for each back edge. Peak operand depth accounts for all paths without accumulating across iterations. Prefix chains use the token and work budgets, not the nesting budget. A successful parse does not execute initializers, assignments, or the final expression.

No slot is cleared when control leaves a block. In a prepared Script, every reference points to the nearest declaration, and that declaration's initializer precedes the reference. Statement branches either enter a block at its start or skip it; jumps may leave scopes but cannot enter a suffix of a block from outside it. A `continue` enters the test or update outside the target loop's body scope. The back edge after a truthy `do` test starts a new entry at the top of the body, never partway through. Thus a reference to a block binding can be reached only after that binding's initializer executed in the current entry of its declaring block; a jump skipping initialization also skips all uses for that entry. Exited slots are inaccessible until initialization on a subsequent entry, so unused or stale slots have no effect.

The evaluator first checks an inclusive ceiling of 4,096 prepared instructions (`EvalError::LimitExceeded`), including skipped paths and their jumps, even when the parser is given higher limits. This bounds temporary storage to at most 2,048 tagged operand slots and 2,047 optional binding slots (each declaration needs at least two instructions and the final expression at least one). Both vectors reserve storage fallibly; bindings start empty and untaken paths can leave them empty. The evaluator checks jump targets, requiring all edges except `LoopBack` to go strictly forward. `LoopBack` must go strictly backward. Both backward and forward unconditional statement jumps require an empty operand stack. Reads and writes must target initialized slots, initializers must target in-range slots and can replace only a value from the same initializer instruction, and assignments must target mutable slots. Malformed reached instructions are distinct from resource exhaustion (`EvalError::InvalidScript`).

Each evaluation gets a separate fixed budget of 16,384 dispatches. Every dispatched instruction costs one unit, including short-circuit branches, loop tests, `for` initializer and update instructions, `break`, `continue`, and loop back edges. Skipped instructions cost no dispatches, and reaching the end costs none. A script that finishes on dispatch 16,384 succeeds; if it needs another dispatch, evaluation stops before running that instruction and returns `EvalError::DispatchLimitExceeded`. Even `while (true) {}`, `for (;;) {}`, and `do {} while (true);` cost three dispatches per complete iteration (literal, conditional jump, backward jump). The budget and all binding state reset on the next evaluation.

## Gaps

This is a standalone prototype against ECMA-262, 16th edition (2025), especially its lexical grammar, decimal and explicitly prefixed Number literals, Boolean and `null` literals, `ToBoolean` and `ToNumber` for supported primitive values, `ToInt32` and `ToUint32`, Number bitwise operations, strict and loose equality and relational comparison for those values, and expression grammar. It does not implement general Script or Module syntax or their full early-error rules, ASI, value types other than Number, Boolean, Null, and Undefined (including strings, BigInt, and objects), other coercions, the browser `IsHTMLDDA` equality exception, other unary or binary operators, calls, host hooks, general expression statements, a runtime temporal dead zone, unbraced control bodies and `else if`, labels and labeled jumps, `switch`, general global lookup or writes, optional chaining, other declaration forms, other loop forms (including `for-in` and `for-of`), assignment expressions, chained assignments, exponentiation (including `**=`), expression-valued increment/decrement, property targets, regular expression literals, hashbang comments or Annex B behavior (including HTML-like comments), alternate numeric literal syntax or JavaScript source represented as arbitrary UTF-16 code units. It does not implement host cancellation, general JavaScript execution, or renderer integration. Allocator, toolchain and platform behavior are outside the parser's guarantees.
